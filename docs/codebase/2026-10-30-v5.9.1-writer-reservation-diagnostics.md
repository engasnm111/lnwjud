# v5.9.1 source candidate — shared writer-reservation diagnostics (#216)

The `recovery_status` and `self_heal_plan` read-only responses now include
`writerReservations` when the shell provider returns authenticated admission
diagnostics. The observation refers to the **global shared reservation index**,
not to task ownership or to the processes visible in the current MCP session.

- `durable_shell_reservations`, `managed_writer_reservations`,
  `unresolved_reservations`, `unreadable_reservations`, and
  `durable_shell_limit` are separately reported.
- `by_mutation_kind` aggregates marker classes, including
  `opaque_uncontained`, `opaque_contained_process`, `synchronous_mutation`,
  `repository_import`, `opaque`, `unreadable`, and `unknown`.
- Reservation IDs, client IDs, workspace IDs, PID/start identities, and raw
  filenames are not returned by this summary.
- `status_basis: held_reservations_not_process_liveness` and
  `terminal_proof: not_observed` explicitly prevent interpreting zero scoped
  running tasks as proof that any reservation is stale.
- If the provider cannot supply a structurally valid admission observation,
  `writerReservations.status` is `unknown` or `unavailable`; overall
  `observationState` is `partial`. No invented zero-capacity assertion is made.
- `recovery: no_automatic_reclamation` is a diagnostics-only statement; no
  marker is removed, writer lease reset, process terminated or task admitted
  by this change.

## Legacy Windows reservations (#238)

The bounded `task_list` admission `blockers` include `marker_origin`,
`owner_binding`, and `terminal_proof: not_observed`. `legacy_unbound`
includes original v1 markers migrated to v2 with `legacy: true`, and old
unattributed task roots reconstructed after upgrade. A recorded native attempt
identifies only a syntactically valid owner/session/attempt/epoch binding; it
is **not** independent proof that the native service accepted it or that all
descendants terminated. Raw task/client/workspace/receipt path data stay private.
Unreadable markers are retained as blockers.

Migration retains the `legacy` flag and refuses PID-only automatic reclaim of
newly migrated legacy markers. Already-migrated v2 records from earlier
versions may lack that flag: `v2_unbound` does not prove modern provenance.
The affected historical reservations require a separate owner audit, not a
retroactive conclusion from marker format alone.

Existing nonlegacy v2 synchronous writers keep
their own scoped behavior. There is **no general force-unlock API**: a
legacy marker without a verifiable native owner/terminal receipt cannot be
authenticated retroactively, even if the current session has zero tasks or
the global reservation count later becomes zero. Do not erase/quarantine old
markers or treat a new zero count as historical termination evidence.
An owner/support recovery must first establish independent historical
terminal/descendant proof for the exact affected attempt, or retain the hold.

This is **not** the full #216 fix. macOS descendants that escape the managed
process group, interrupted native owners and legacy `opaque_uncontained`
markers still require independent terminal-owner/descendant proof. Never treat
a vanished launcher PID or empty session-scoped task list as enough to release
a global reservation. The installed v5.9.0 binaries do not contain this
v5.9.1 source-candidate change until a subsequent verified release.

Validation: `corepack pnpm@10.15.0 --filter @lnwjud/mcp-server exec vitest run
src/self-heal.test.ts src/upgrade-runtime.test.ts --fileParallelism=false` (32
passing tests) and `corepack pnpm@10.15.0 --filter @lnwjud/mcp-server
typecheck` (passed) on 2026-10-30. These results do not prove native updater
installation, signed package acceptance, macOS descendant containment or
recovery of an actual customer reservation index.
