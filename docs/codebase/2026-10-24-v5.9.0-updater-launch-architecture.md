# v5.9.0 Windows updater launch architecture feasibility

**Status: feasibility decision only. No launcher or production update authority is implemented by this review. No release gate is cleared.**

## Decision

Candidate C is the best next design for an isolated Windows feasibility experiment, but it is not ready for production implementation or acceptance. It places application process creation in the trusted Windows service, creates the child suspended in a service-owned Job at process creation, durably registers the child and launch intent, then resumes it. The user-session shim does not create the application process and cannot choose the executable or A/B slot.

Candidates A and B both let the shim create a suspended child before the service binds it. Candidate A's reservation is stronger than B's extra sharing barrier, but the independent review found that neither proposal proves ownership or cessation when the shim exits in that interval. B adds another synchronization order without closing the interval. Candidate C removes that particular creator gap only if Job membership, Job-handle exclusivity, and kill-on-last-handle behavior are demonstrated on the installed service.

The independent cross-review found that C still does not complete the updater contract. Its pre-registration state remains held after recovery; it has no durable user-session agent to restore the GUI and Tunnel after a service restart; its cross-session STDIO relay is only proposed; and the updater/admission/containment handoff has no complete durable state machine. Do not treat service-owned creation as proof of unattended restart or rollback.

## Authority boundaries

- The enrolled updater authority owns publisher trust, installation identity, transaction state, slot selection, trial health, and rollback decisions.
- The maintenance admission broker owns the writer and maintenance reservation it is assigned. It must not independently decide updater transaction recovery.
- The Windows containment service owns its process and Job handles, launch attempts, and evidence of process lifetime. It must accept only a fixed, authenticated launch request tied to the enrolled installation and exact selection generation.
- The stable user-session shim is a bounded client. It does not accept an executable path, shell command, environment block, slot selection, arbitrary Electron arguments, or process token from its caller.

These roles require an authenticated, generation-fenced protocol with durable predecessor state, idempotent inspect/retry, explicit cancellation, and fail-closed recovery for every service-death point. A JSON `approved` value or request ID alone is not authorization. No component may reopen admission from timeout or an unverified PID observation.

## Candidate C launch contract to prove

1. The service authenticates the actual named-pipe caller and retains a primary token derived from that caller. It verifies the original user SID, logon identity, and nonzero session without accepting a caller-supplied SID, PID, session ID, or elevated linked token.
2. The updater and admission authority authorize a fixed launch intent bound to installation identity, selected slot digest and generation, caller/logon/session, transaction epoch, attempt ID, and service-owner generation.
3. The service persists launch intent before process creation. It creates a fresh Job with a service-only DACL and `KILL_ON_JOB_CLOSE`, refuses a preexisting named Job, and uses `PROC_THREAD_ATTRIBUTE_JOB_LIST` with suspended creation. It must not fall back to create-then-assign.
4. The service creates only the executable derived from the enrolled root and authenticated A/B selection. It retains the process and thread handles, verifies image identity and Job membership, then durably records process identity and authority acknowledgement before resume.
5. A lost RPC response is resolved by inspecting the same attempt. It must never cause a duplicate launch. On any disagreement, crash, or missing proof, the writer/admission hold remains closed.
6. Before migrations, mutable workspace operations, or Tunnel work, the application obtains a startup disposition bound to the current enrollment, selection, and admission generation.

Windows documents creation-time Job assignment through [`UpdateProcThreadAttribute`](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-updateprocthreadattribute) and Job lifetime/termination rules in [Job Objects](https://learn.microsoft.com/en-us/windows/win32/procthread/job-objects). The guarantee is conditional on exclusive protected Job-handle ownership, no handle leakage, no breakaway, and complete coverage of processes that can perform admitted writes.

## Current source is not the proposed contract

`native/windows-containment-helper/ContainedProcess.cs` already uses `PROC_THREAD_ATTRIBUTE_JOB_LIST`, creates the child suspended, checks Job membership, calls a pre-resume hook, and then resumes. That is reusable evidence for a feasibility experiment. The current path also uses NUL stdin, inherited standard handles, a null desktop, and `CREATE_NO_WINDOW`; its own comments specify headless service-side CLI workers. Do not reuse it as proof of an interactive Electron launch or cross-session MCP STDIO.

`AuthenticatedPipeCaller` duplicates a pipe caller's token and preserves its session. The current generic `run_process` RPC still accepts an executable path after bounded validation, and the existing attempt ledger deliberately restores dispatched/running work as `TerminationUnknown`. Neither is an enrolled, fixed-purpose updater launch ABI.

Interactive launch must prove access to the authenticated user's existing `winsta0\\default` desktop, the correct loaded profile, HKCU, AppData, DPAPI, and a user-token environment without changing desktop ACLs or launching into session 0. Microsoft's [`CreateProcessAsUserW`](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-createprocessasuserw) documentation covers desktop, profile, and session requirements. It also does not allow standard handles to be inherited across Terminal Services sessions. The current CLI process implementation therefore cannot establish STDIO compatibility.

## Unresolved acceptance gates

- **Recovery after create, before durable PID registration:** creation-time Job membership can contain the child, but C keeps this attempt held because the existing recovery contract has no accepted cessation proof. Define and review evidence that can safely settle it, or explicitly retain attended recovery. An absent Job name, timeout, or PID enumeration alone does not currently satisfy the contract.
- **Recovery after service restart:** C's service-owned Job intentionally terminates the GUI and its descendants when the last Job handle closes. This can stop the Tunnel and interrupt unsaved work. There is no persistent authenticated session agent or guaranteed reauthentication path to start the selected app and restore the same Tunnel after SCM restart.
- **Inter-service commit protocol:** define exact persisted states, owner generations, idempotent retries, ack ordering, cancellation, and recovery across updater, admission, and containment service restarts. A stale resume acknowledgement must not override a newer maintenance closure.
- **CLI/STDIO:** specify a fixed compatibility allowlist for existing packaged profile/workspace/STDIO entry points, deep links, file associations, `.cmd` shims, and exit codes. Implement byte-preserving authenticated pipes with bounded backpressure, EOF ordering, independent stream drain, cancellation, and exact exit propagation. No service diagnostics may enter application stdout.
- **GUI lifetime:** test profile/session access, nested Electron Jobs, sandbox subprocesses, delegated writers, locked/RDP/logoff and multiple-session behavior, graceful application shutdown, and all writer descendants under an installed SCM service.
- **Trust and enrollment:** no production signer, enrolled installation policy, stable-service package, or signed enrollment producer has been accepted. The current unsigned installation cannot enroll itself or establish source identity.
- **Real update acceptance:** no signed update over an older signed installation, restart, exact-version independent health, Tunnel restoration, injected failure, rollback, and post-rollback health/Tunnel sequence has passed. Public release remains prohibited until the user's full acceptance requirement passes for every advertised platform.

## Safe next proof unit

Run only in a disposable Windows x64 test environment with separate test product IDs, service and pipe names, signing roots, installation root, and application data. First launch a benign GUI fixture and a streaming STDIO fixture as a standard user through the installed service. Inject service termination before creation, after creation but before durable registration, after registration but before resume, and after resume but before RPC response. Verify no unowned process or writer survives, no retry duplicates a child, no stale acknowledgement reopens admission, and the exact user session/profile is used. Then test the defined session-recovery policy.

This experiment is not authorized for the live workstation's production service, installed app data, or connected Tunnel. The user's live Tunnel remains untouched; Factory Reset must not be run against live data as an updater test.

## Design principles applied

- **Model the Domain:** transaction selection, maintenance admission, and process lifetime have different owners and records.
- **Exhaust the Design Space:** A/B both use launcher-owned process creation; C is the distinct service-owned feasibility candidate, with its service-crash and TTY/STDIO tradeoffs explicit.
- **Prove It Works:** source-level Job mechanics and the installed v5.9.0 smoke test do not prove current-source installation or signed updater acceptance.
- **Technical Writing:** the accepted status is stated separately from proposed behavior and missing proof.
