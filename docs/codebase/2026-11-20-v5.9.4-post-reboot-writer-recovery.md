# v5.9.4 — post-reboot recovery for persisted termination-unknown writer attempts (#260)

Issue #260 reported ten held writer reservations after a full Windows restart
(one durable-shell and nine managed-writer blockers, all
`marker_origin: native_attempt_recorded_unverified`,
`terminal_proof: not_observed`). A later write operation still returned a
conflict, and `self_heal_plan` offered only `reindex-workspace`. The report did
not claim the original native processes were dead.

## Root cause

Two separate dead ends existed after a restart:

1. **Persisted termination-unknown ledger records were never reconcilable.**
   The protected service persists its attempt ledger. On service start it
   downgrades a persisted `DispatchCommitted` or `Running` record to
   `TerminationUnknown` because the in-memory Job handle is gone. An attempt
   that was dispatched but had not yet recorded its post-membership target PID
   could not be finalized by `inspect`: the Job is absent, but a missing Job
   alone cannot prove that the target was ever contained. The only remaining
   route, `recover_after_reboot`, refused every existing nonterminal record with
   `SERVICE_RECOVERY_EXISTING_ATTEMPT_UNVERIFIED`. A verified newer OS boot —
   which does prove that no earlier-boot process can survive — therefore did not
   release the record.
2. **Durable-shell tasks never requested reboot recovery.** The durable-shell
   reconciliation path attempted only abort-before-launch and then kept a
   `termination_unverified` task. It did not call `recover_after_reboot`, and
   its proof predicate rejected any nonterminal task state. The shared
   reservation marker therefore stayed held even if the service could prove
   interruption.

`recovery_status` and `self_heal_plan` also did not name the supported
reconciliation call, so the operator-facing report looked like there was no
recovery path at all.

## Fix

- `ServiceAttemptLedger.RecoverAfterReboot` may now finalize an existing
  persisted `TerminationUnknown` record as `interrupted` with exit code 125.
  Every existing precondition still applies before the ledger is touched: the
  exact identity and authenticated caller SID must match, the original marker
  timestamp must be more than five seconds older than the current boot, and the
  attempt-named Job must be absent in this boot. Live `Prepared`,
  `DispatchCommitted` and `Running` records, import holds
  (`SERVICE_RECOVERY_IMPORT_HOLD_UNVERIFIED`) and active or unknown Jobs remain
  refused.
- The durable-shell store now asks the authenticated service for the same
  new-boot reconciliation when a native termination proof is unavailable, the
  recorded local owner is proven gone and the task is already
  `termination_unverified` (or its deadline has passed). A terminal
  `interrupted` proof finalizes the task as `failed` with exit code 125 without
  inventing a successful exit; a refusal keeps the marker and task fail-closed.
  The proof predicate accepts the newly finalized interrupted result.
- `self_heal_plan` now reports `by_marker_origin` counts plus a
  `supportedRecovery` entry, and `recovery_status` mirrors it as
  `recommendedActions`, when native-bound holds exist. The suggested call is
  `workspace_writer_lease_acquire` with `recoverAbandoned` and `userConfirmed`
  after a full Windows restart. The diagnostics still do not reclaim anything,
  and the entry states that active, import-held, conflicting or unverifiable
  records remain blocked.

## Safety invariants preserved

- No PID-only reclaim, marker deletion, quarantine, force-unlock, concurrency
  limit change, process kill or service bypass was added.
- A full OS restart is the proof boundary. Service restart alone does not
  satisfy it; liveness of the current boot's process tree is never inferred from
  a missing PID.
- Import holds keep their writer fence until service-owned publication evidence
  clears them.
- Legacy, v2-unbound and unreadable reservations remain held and unsupported by
  this route.

## Validation

- `dotnet run --project native/windows-containment-helper/tests/ContainmentNativeTests.csproj -c Release -- post-reboot-recovery`
  covers a missing attempt, an owner mismatch, an active Job refusal, a
  persisted termination-unknown record that recovers to interrupted/125, its
  persisted idempotency, a live dispatch that stays refused, and an import hold
  that stays held.
- `packages/capabilities/src/workspace-writer-admission-recovery.test.ts` adds a
  durable-shell case whose task is finalized by the new-boot route and whose
  shared marker is released only after that proof.
- `packages/mcp-server/src/self-heal.test.ts` verifies the
  `by_marker_origin`, `supportedRecovery`, `recommendedActions` and
  privacy-preserving manual issue without leaking reservation identities.

Installed-service acceptance on an exact-SHA build and a real Windows restart
remain part of the release gate; the focused native route and mocked TypeScript
tests do not prove SCM installation or authenticated pipe behavior.
