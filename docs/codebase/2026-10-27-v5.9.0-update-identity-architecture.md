# Proposed update identity and authorization contract

Status: partially implemented. An inactive stable-identity primitive, fresh v2 signature authentication and a v2 producer exist in Node and native code and pass public-fixture tests. The enrollment consumer still uses the v1 envelope described in `native/update-worker/release-metadata-contract.md`; production build-evidence verification, retained acceptance and transaction recovery for v2 are not implemented. Production trust remains unconfigured and the updater remains unavailable.

## Problem

A fresh v1 release envelope expires within 24 hours. Both the producer and native consumer bind the next update to the exact previously accepted envelope digest. Renewing the authorization changes that digest even when the application and build evidence are unchanged. Installations of the same release can therefore form different predecessor cohorts, each needing its own successor. Historical verification proves that an existing installation accepted an earlier envelope; it neither makes that envelope fresh for a new installation nor permits an expired offer to run.

The first signed installation also has no honest v1 predecessor, although the producer requires one. Skipping predecessor verification or manufacturing a previous release would weaken the trust boundary. Independently of these issues, v1 recovery can become unavailable if its authorization expires while a transaction is incomplete.

## Usage

The protected producer has two explicit operations. Both require actual completed build evidence and sign only after its verification:

```text
baseline: immutable release identity + fresh enrollment authorization
update:   immutable release identity + fresh authorization for one exact predecessor identity
```

An installation accepts a baseline only as part of a protected first-enrollment transaction. An update offer is eligible only for the installed predecessor identity, a higher release sequence and version, compatible contracts and an unexpired authorization. A publisher supplies separate fresh offers for each explicitly supported predecessor; unsupported versions require a verified intermediate update or a separately authorized recovery path. The user still confirms the exact target once before the native transaction proceeds.

## Shape and invariants

Use a new wire version and signature domain rather than interpreting v1 bytes with new meaning. A signed envelope contains an exact immutable `release` object and a separate `baseline` or `update` authorization. Baseline authorization has no invented predecessor or rollback target. Update authorization identifies exactly one stable predecessor and provides a one-attempt recovery grant. Initial enrollment accepts only the baseline purpose; offer and recovery entry points accept only the update purpose.

The immutable object contains product and release ID, channel and target, version and release sequence, source repository/commit/workflow/ref/run/attempt, build-evidence identity, artifact and provenance names/hashes/sizes, and migration/worker/service compatibility contracts. Its stable identity is a domain-separated SHA-256 over a deterministic, schema-versioned, length-prefixed UTF-8 encoding of every validated immutable field. Traverse the exact schema's fields in ordinal order, include field names and type boundaries, and reject unknown fields and noncanonical values before encoding. Do not use ambient JSON property order, locale formatting, version alone, or a caller-supplied digest. Changing the identity schema requires a new identity domain/version. Cross-language vectors must compare encoded bytes as well as hashes.

Issuance, expiry, signature, signing-key representation, authorization purpose, predecessor and recovery grant are outside the immutable identity. Refreshing an authorization must reuse the same exact immutable release and build evidence. A new binary, build/run, evidence bundle, target, sequence or compatibility contract produces a different identity. Refreshing does not increment sequence, clear quarantine, overwrite retained acceptance evidence, or replace an authorization pinned to an active transaction.

An identity digest is not an authorization. The native authority retains the exact accepted signed envelope, protected acceptance receipt and time, installed slot and data generation, trust generation/revision and anti-replay floors. It reauthenticates the retained bytes at the protected acceptance time, recomputes the immutable identity and checks current revocation and explicit historical-recovery policy. An expired accepted envelope is evidence of a past acceptance only. An expired offer cannot start a new enrollment or update.

For recovery, the protected transaction records the exact accepted candidate envelope and baseline envelope, selected predecessor identity, candidate package, transaction ID, trust generation/revision and remaining attempt. A protected receipt must prove that the candidate and user consent were accepted before the offer expired. The one-use recovery grant is bound to that nonterminal transaction rather than an invented wall-clock deadline: after a long shutdown it can only restore the exact previously accepted application/data pair, never authorize another forward update. Current locally known revocation and historical-recovery policy still apply; an offline machine cannot claim awareness of a remote revocation it has not received. Candidate acceptance, identity, anti-replay advancement, consent, selected pair and recovery grant must be committed atomically before mutation. Failure and candidate quarantine are recorded atomically before rollback admission. Consuming the one attempt and starting rollback must be journaled before effects; a crash resumes that same idempotent attempt under a verified ownership-fence chain. Verified terminal success or rollback retires the grant permanently. Unknown state, owner cessation or current policy remains held.

Re-enrollment must not reset a surviving protected high-water mark. Missing, corrupt or incomplete protected state is not automatically a fresh installation. If all durable authority has been erased, the application cannot distinguish a first installation from destructive reset; a separately authorized recovery/reset policy is required.

## Integration

- The schema, producer and native verifier must agree on the same v2 domain, exact variant field sets and deterministic identity encoding. Ordinary v1 envelopes must not be silently reinterpreted as v2.
- The producer authenticates every predecessor envelope and its real package/provenance before issuing an update edge. Baseline production still requires exact verified build and attestation evidence before the signer secret is read.
- Enrollment layout must bind to the authenticated stable release identity and actual package/layout bytes. Exact signed authorization and layout bytes remain retained for acceptance and audit; a newly signed layout cannot replace evidence for an existing transaction.
- The retained native baseline and future durable serialization must distinguish metadata version and purpose, retain original bytes and acceptance receipt, and reject ambiguous records. Current source has no production retained-baseline persistence or enrollment authority to claim as working.
- The updater feed must deliver a current signed offer for the installed predecessor identity without trusting a network-supplied identity as authority. Availability for old releases requires retaining real predecessor evidence and publishing explicit supported transitions.
- The P-256 metadata signer, GitHub OIDC build attestation and Windows Authenticode publisher identity are separate authorities. The provisioned GitHub secret has only metadata readback so far; a protected sign/verify, key rotation/recovery and actual attested builds remain open.

## Signer and evidence isolation

The verifier must run without the signing secret under a separate security identity from the signer. Excluding the secret from the verifier's child environment alone is insufficient while it remains in a parent process accessible to that identity. The signer must authenticate an immutable evidence handoff that binds the exact candidate, policy, workflow run and attempt, artifacts and attestation bundles; a caller-supplied success flag or ordinary unsigned artifact is not authority.

A fixed-purpose native evidence operation can reuse the existing enrollment attestation verifier's process containment and evidence checks, while accepting a strictly validated unsigned candidate without treating it as an authenticated release. Its executable, inputs and protected scratch directory must remain pinned until the whole verifier process tree has stopped and output has drained. Unknown process liveness or cleanup remains held. Secure helper bootstrap, scratch directory ACLs, actual GitHub attestation verification and the authenticated cross-identity handoff remain unimplemented and must be tested before enabling production signing. The current Node verifier tests only local file pinning and environment handling; they do not prove these properties.

The scratch owner must start from a trusted service-owned base, pin non-reparse ancestry root first, and atomically create a fresh leaf with its final protected DACL; an existing leaf is a collision, never a directory to adopt. Immutable, pinned GitHub configuration and a separate writable temporary directory have different permissions and lifetimes. Hold both through observed Job-zero and output drain. Cleanup must not recursively follow verifier-created content: remove only known files by retained identity, then remove empty directories; unknown or nonempty content remains explicitly quarantined. Existing `WindowsStoreIO` and `PinnedDirectory` provide partial primitives but do not satisfy this complete contract. In particular, an ACL granting full control to the same SID as the verifier does not isolate a hostile same-user process; a distinct principal and restricted verifier identity are still needed for that boundary.

The existing containment service provisions a SYSTEM/Administrators-protected ProgramData store, but the attestation preflight currently runs directly under its caller and does not use that store. The available caller-token launcher preserves the caller's identity; it is not a separate verifier principal. Routing `gh` through the service without a restricted token would instead run it with elevated service privileges. Isolated GitHub-hosted verification and signing runners may avoid that local principal-provisioning work, but their evidence handoff must still be authenticated and bound to the exact workflow, inputs and policy before the signing runner receives the key.

The existing reusable package builder separates build and attestation jobs, but its package attestation does not authorize a new signing-evidence receipt. One possible signing boundary is a pinned, reviewed workflow that explicitly trusts GitHub's job dependency outputs and artifact delivery as its authority: a key-free verification job reports exact input digests and artifact ID to a fresh signing job, which checks successful dependency status, independently hashes all downloaded inputs and signs only those exact bytes. This is an orchestration trust contract, not a cryptographically authenticated receipt, and requires review of the immutable workflow, trusted verifier, job outputs, secret scope, runner isolation and every binding before implementation. GitHub's [artifact documentation](https://docs.github.com/en/actions/tutorials/store-and-share-data#validating-artifacts) says a digest mismatch can be a warning, so the signing job must fail closed on a mismatch. A cryptographic receipt is an alternative only if its verifier has an independently established trust boundary; running an uncontained `gh` process in the signing job before introducing the key merely moves the unresolved process-lifetime problem.

Independent review found this option viable only if the protected verifier job itself is explicitly trusted to make the verification decision. A compromised verifier can approve false digests; runner separation protects the key but does not provide a second independent approval. A versioned, strictly parsed result must bind repository, protected event/ref, source commit, orchestrator and verifier workflow revisions, exact producing run and attempt, target, trust-policy digest and attestation authority, candidate bytes, purpose and stable identity, package/provenance/bundle names, sizes and digests, transport artifact ID and owner, predecessor evidence, recovery and compatibility fields. A digest can summarize this result only after the signer validates the complete result against expectations from trusted configuration. Reject missing or extra files, incomplete outputs, unexpected schemas, non-successful dependencies, and partial reruns whose producing attempt cannot be proven. The signing runner must execute only trusted pinned control code, never candidate content or an untrusted cache, and obtain the key only within the protected signing job. The exact hosted positive and negative cases remain to be implemented and run; none of these statements activates signing.

The proposed result manifest contains a version, the verification repository/run/attempt, policy digest, purpose, and fixed file roles with canonical basename, size and SHA-256. Candidate roles cover the exact unsigned descriptor, package, provenance and both attestation bundles. Update purpose adds the exact predecessor envelope, package and provenance; baseline must not carry them. Derive source/build run and attempt, target, recovery, compatibility and stable identity from the strictly validated candidate rather than making duplicated manifest claims authoritative. Authenticate and recompute the predecessor identity for an update. The signer receives the expected successful dependency, manifest digest and transport artifact ID separately from trusted orchestration, retrieves the artifact by ID with its owner/run checked, hashes the original manifest bytes and all fixed-role files, and rejects anything not exactly bound. The artifact ID is outside the manifest because it exists only after the manifest is uploaded. Build and verification attempts are distinct: initially reject a partially rerun signing attempt if the verification-producing attempt cannot independently be proven current. Retain or otherwise protect the checked bytes through signing; matching hashes after releasing mutable inputs do not establish that the signed bytes are the checked bytes. A strict, non-authorizing manifest parser now has fixture tests. Orchestration, actual file binding and signer integration remain unimplemented; the parser cannot authenticate its own manifest.

The proposed production entry point is specific to the reviewed workflow: it obtains workflow context and the expected dependency outputs from fixed expressions, checks the current attempt and the unique successful verification job through GitHub's API, checks the exact artifact ID and owning run, and performs download, binding and signing in one trusted process. Artifact metadata alone does not establish which attempt produced it; reject a signing-only rerun if the verification job is absent from the current attempt. Small metadata and bundle bytes must be retained privately and used directly for signing; large packages may be streamed and bound by digest, then rechecked at publication. Do not execute downloaded content or spawn `gh` on the signing runner after the key is introduced. The first hosted implementation must remain diagnostic and key-free until positive and negative provenance tests pass.

## Alternatives and reconciliation

A detached genesis descriptor and a discriminated baseline/update envelope were independently compared. Both require changes to retained baseline verification, layout binding and producer evidence. The shared discriminated envelope is smaller, but neither original sketch solved the renewal cohorts. This design retains the discriminated boundary and adds stable identity, while retaining exact authorization bytes for each protected transaction. A second signature on the immutable object is unnecessary if the complete envelope is authenticated and retained acceptance is protected.

Longer metadata expiry only postpones the cohort problem. A version range or unbounded predecessor wildcard would hide compatibility and rollback choices; one exact predecessor per offer keeps each transition explicit. This is an accepted publishing cost, not a claim that the update feed exists.

Implementation must reconcile this design with the existing transaction architecture and record any accepted deviation here before production activation. Tests must cover two differently refreshed authorizations of the same immutable release, one successor for both, changed immutable fields, multiple explicit predecessor paths, expired offline offers, rollback across offer expiry, signature/domain confusion, replay, clock rollback, quarantine, and crash/concurrent enrollment boundaries. Fixture signatures are not hosted or installed updater acceptance. No release is permitted until the actual one-confirmation silent install, relaunch, health, Tunnel restoration and rollback acceptance pass.
