# v5.9.0 updater transaction architecture

Status: selected design base for implementation and feasibility work. This is not evidence that automatic updating has been implemented or accepted. Do not tag or publish v5.9.0 until the signed target-native success and rollback gates below pass.

## User contract

The user sees the target version and confirms once. That confirmation binds to the authenticated offer digest, platform, architecture, installation identity, and exact previous application/data generation. After confirmation, lnwjud waits for admitted work to finish, closes new writes, records the current Tunnel intent, stops Tunnel, and exits. The installed authority activates the candidate without an installer wizard or another application prompt, relaunches the app, verifies health, and restores Tunnel if it was connected before the update.

The update is successful only after independent evidence identifies the exact new package and running process, confirms the selected data generation is usable, and confirms the prior Tunnel identity is connected when applicable. A failed candidate is stopped with positive cessation evidence. The authority then restores the exact prior application and data generation, restarts it, and verifies health and Tunnel before reopening writes. Unknown process ownership, liveness, selection, data, or journal state keeps admission closed and presents recovery.

The feasibility fixture may use a dedicated test signing identity to prove local mechanics. That is separate from official release evidence. A local unsigned installer or synthetic receipt cannot satisfy the release gate.

## Architecture decision

An independent cross-review scored three structurally different proposals against the six-item rubric. Candidate 1 scored 23/30, candidate 2 scored 19/30, and candidate 3 scored 14/30. Scores compare design completeness, not implementation or acceptance.

Use candidate 1 as the base: one native update authority owns enrollment, trust, admission, transaction journal, launch, health, application selection, data selection, commit, and rollback. It selects an immutable application slot together with an isolated data generation through one durable descriptor. The Desktop process uses a small typed API and never sends executable paths, arbitrary commands, or transaction phases.

Incorporate candidate 2's compatibility obligations for existing launch entry points, shortcuts, file associations, CLI, and MCP STDIO. Incorporate candidate 3's capability preflight and explicit unavailable result for installations that are not safely enrolled. Do not use candidate 2's pair of active-directory renames or add another admission service as an independent transaction owner.

Candidate 1 is not production-ready. Its service/session implementation, cessation proof, platform adapters, data inventory, signing enrollment, and acceptance producers remain to be built and validated.

## Ownership and persisted state

The stable authority lives outside replaceable application slots. On Windows it must hand off a GUI process only into the authenticated interactive session while retaining native process ownership proof. A session agent may present status and reconnect to the authority but cannot select versions or advance the journal. macOS requires a signed enrolled launcher/helper arrangement that preserves Finder, Dock, deep links, file associations, and STDIO. The native Windows and macOS implementations share transaction rules, not assumptions about process or filesystem behavior.

One atomic descriptor identifies installation owner or user cohort, authority epoch, application slot and manifest, data generation and manifest, and selection generation. The journal binds the same descriptor to consent, authenticated offer, predecessor, Tunnel intent, admission epoch, launch attempts, observations, and final result. It stores no reusable Tunnel secret. Revisions use compare-and-swap, and every external effect has a durable intent and an identity that makes retry idempotent.

The data generation includes the SQLite database and every mutable file or migration-owned resource required by the candidate. User workspaces and remote systems are never copied or mutated as part of an update. Tunnel credentials remain in their existing OS protection domain. Multiple logged-in users and machine-wide installations require an explicit owner/cohort model before rollout.

## Transaction outline

1. Authenticate and stage the exact package before asking the user. Check its release envelope, digest, platform, architecture, publisher, file manifest, policy, sequence, enrollment, and compatibility.
2. Ask once for the version. Persist consent against the offer digest and exact predecessor. A changed offer or predecessor invalidates that consent.
3. Persist a maintenance intent, close admission globally, and drain all known work. Live or unknown writers keep the operation held.
4. Persist Tunnel stop intent and desired pre-update state. Stop only the enrolled Tunnel and verify stopped state.
5. Verify the complete candidate slot and create an isolated candidate data generation. Publish the application/data descriptor atomically and read it back.
6. Persist one launch attempt before starting the candidate. On a lost response or restart, inspect the same attempt instead of launching a duplicate.
7. Independently verify executable identity, version, package manifest, data readiness, critical native services, and Tunnel identity/connectivity. Ordinary writes remain closed during trial.
8. Commit the candidate descriptor and release admission only after all required evidence is durable.
9. On failure, prove candidate cessation, select the exact predecessor application/data pair, launch once, and verify its digest, health, and prior Tunnel state. Release admission only after rollback verification. Otherwise remain held for attended recovery.

An application self-report or process-exists check is not independent health evidence. A timeout, missing PID, or helper restart is not proof that writers have stopped.

## Reuse gaps that must be resolved

- The production worker still advertises automatic installation as unavailable (`TRANSACTION_BOOTSTRAP_ONLY`), and request commands end in pre-authentication refusal (`PACKAGE_AUTHENTICATION_UNAVAILABLE`). `status` reads staged and published A/B transaction records under the existing native store lock and holds pending publication, malformed, noncanonical, or nonterminal journals, missing slot selection, or a terminal selection mismatch without writing. `recover` invokes `RecoverPublications` only when a transaction or slot publication is staged; canonical successor and selection checks run under the same native lock before publication, then the worker rechecks state and keeps nonterminal transactions held. Invalid or conflicting staged bytes fail closed. This bounded publication recovery does not add package authentication, installation, health, Tunnel restoration, rollback, or installation capability.
- UpdateTransactionStore is Windows-specific. A storage interface and target-specific crash-safe implementations are required.
- ReleaseMetadataVerifier now accepts only the exact Windows x64 NSIS and macOS x64/arm64 ZIP metadata identities. This does not add a macOS transaction implementation or enable installation on any target.
- Sequence semantics are fixed: the retained baseline sequence is the last committed release; `HighestAcceptedSequence` is a monotonic replay floor. The production authority must CAS-advance the floor when it binds user consent to an authenticated offer, before any external effect. Normal offers must exceed both values. Rollback restores the exact prior application/data baseline without lowering the floor; recovery is limited to the exact quarantined failed candidate at the floor and its one authorized attempt. The verifier enforces these read-side checks, but the production consent-bound writer/CAS is not implemented yet, so this decision does not enable updating.
- UpdateTransactionJournal records phases and digests, but not independent health, writer cessation, or data-generation evidence. The current prototype refuses `HealthVerified`, `Committed`, and `RollbackVerified` transitions and decoded records until a trusted native evidence contract exists; this keeps the worker fail-closed and does not implement a usable updater.
- RollbackUnverified is a held, nonterminal journal state. A native store regression confirms the hold survives reopen and blocks a successor transaction. It cannot advance to a verified state without a dedicated recovery-evidence contract; attended recovery remains required until that path is implemented.
- Current receipt validation checks claimed version and prompt fields, but does not itself prove consent identity, observed process or data manifests, authority identity, Tunnel observations, or the observation transcript. A trusted native producer and receipt schema extension are required.
- The package workflow consumes updater receipt artifacts but has no receipt producer. Build producers on Windows x64 and macOS x64/arm64, bind them to exact source and workflow runs, and derive receipts from independent OS/UI/network observations.
- Define how a machine-wide application install and multiple user profiles share or separate data generations. A retained baseline must also honor the startup admission protocol and compatible data contract.

## Enrollment and platform scope

The installed candidate was observed at C:\Program Files\lnwjud\lnwjud.exe. It cannot silently grant itself authority from its existing unsigned bytes. A trusted installer or independently managed deployment must enroll the stable authority and bind it to the chosen installation and user/session policy before automatic installation is offered.

Windows x64 and macOS x64/arm64 are the current signed updater receipt targets. Linux and portable paths remain gated by their own verified updater contract. A platform without a production transaction and native acceptance producer must expose automatic installation as unavailable rather than imply that another platform's proof applies.

Installation enrollment must happen before the first update requiring authority. Any operating-system privilege or trust confirmation at update time would violate the one-confirmation user contract, so enrollment belongs in the initial trusted installation or an explicitly managed migration.

## Evidence and release gate

For every target, run an older signed baseline and a newer signed candidate in a disposable enrolled installation. Observe the actual version confirmation once, zero additional installer or app prompts, app exit and automatic relaunch, exact candidate identity, health, the same Tunnel identity, and final connection. Repeat with an injected post-install health failure and verify candidate cessation, exact previous application and data manifests, prior-version restart, health, and Tunnel reconnection.

Receipts must bind source SHA, exact workflow run and attempt, target, old/new package and feed digests, authority build, trust policy, prompt observation, process identity, health transcript, Tunnel observations, and rollback result. Exercise crashes at every intent/effect/publication boundary, reboot, process/helper restart, session loss, disk-full, lost replies, and active external writers. The native producer and independent verifier must reject missing, duplicate, unsigned, cross-target, replayed, or self-asserted evidence.

The installed 5.9.0 candidate's Tunnel Stop/Start smoke test and native helper regression suites are useful containment evidence. They do not test package installation, restart health, automatic Tunnel restoration, or rollback. Release remains blocked until exact-source hosted checks and signed native success and rollback receipts all pass.
