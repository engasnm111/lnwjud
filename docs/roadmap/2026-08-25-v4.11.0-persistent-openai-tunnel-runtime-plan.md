## 1. Clarified product requirement

v4.11.0 must remain local-first. Each user already owns and runs their own:

- lnwjud Desktop installation;
- OpenAI Secure MCP Tunnel (`tunnel_id`);
- `tunnel-client` binary;
- runtime API key stored locally;
- local Desktop MCP endpoint.

Therefore v4.11.0 must **not** introduce a mandatory lnwjud relay server, VPS, domain, Cloudflare hostname, account system, or managed cloud.

The stable remote identity already exists in OpenAI Secure MCP Tunnel: the user configures ChatGPT to the same tunnel once, and `tunnel-client` polls work for that `tunnel_id` and forwards it to the local MCP target.

The problem to solve is local runtime continuity, not creation of another public endpoint.

## 2. Target architecture

```text
ChatGPT / supported OpenAI client
        |
        | Connection: Tunnel
        | same tunnel_id for the life of the installation/profile
        v
OpenAI Secure MCP Tunnel service
        |
        | queues/polls commands for tunnel_id
        v
user-owned tunnel-client runtime
        |
        | local binding may be repaired/reconnected
        v
http://127.0.0.1:<desktop-port>/mcp
        |
        v
lnwjud Desktop MCP
        |
        v
Existing McpApplicationServices / tools / durable tasks
```

Critical invariant:

> **The OpenAI `tunnel_id` is persistent. The local process, local MCP port, and network connection are replaceable.**

## 3. What "static URL" means in this design

The user should not need to buy or maintain a public hostname. OpenAI's tunnel service owns the remote connector endpoint for the tunnel. ChatGPT setup uses **Connection: Tunnel** and the existing tunnel/tunnel ID.

Internally OpenAI's tunnel service exposes MCP traffic by tunnel identity, while `tunnel-client` polls `/v1/tunnels/{tunnel_id}/poll` and posts terminal responses to `/v1/tunnels/{tunnel_id}/response`.

lnwjud should therefore expose in UI:

```text
Persistent Tunnel Identity
Tunnel ID: tunnel_...
Runtime Alias: lnwjud
Status: Connected
Local MCP: 127.0.0.1:<port>/mcp
```

Do not ask normal users to construct or paste OpenAI internal MCP endpoint paths manually. The stable user-facing object is the tunnel selected in ChatGPT.

The new version should reuse these components instead of adding a new network protocol.

## 5. Main v4.11.0 design change

Replace the current concept of "start one tunnel-client child and keep it alive" with a **Tunnel Runtime Reconciler**.

The reconciler continuously asks:

```text
What tunnel identity should this installation serve?
Is Desktop MCP ready?
Is the expected local tunnel runtime already healthy?
Is it attached to the correct tunnel_id?
Is it forwarding to the current Desktop MCP URL?
If not, what is the smallest safe repair?
```

It must never create a new tunnel ID merely because a runtime process disappeared.

## 6. Prefer native tunnel-client runtime supervision

Current official `tunnel-client` supports native runtime lifecycle commands including:

```text
tunnel-client runtimes create
tunnel-client runtimes connect
tunnel-client runtimes list
tunnel-client runtimes status
tunnel-client runtimes stop
tunnel-client runtimes rm
```

For long-lived local operation, v4.11 should prefer a stable runtime alias:

```text
alias = lnwjud
```

Conceptual reconciliation:

```text
1. Start Desktop MCP.
2. Resolve current loopback MCP URL.
3. Read saved tunnel_id and protected runtime key.
4. Check `tunnel-client runtimes status lnwjud`.
5. If runtime is healthy and attached correctly: do nothing.
6. If missing/stale/wrong local binding: reconnect alias `lnwjud`
   to the SAME tunnel_id and current local MCP URL.
7. Verify /healthz, /readyz and control-plane poll health.
8. Keep monitoring at a low-cost interval.
```

If native `runtimes` commands are unavailable in an older tunnel-client, retain the existing profile + `run --profile lnwjud` path as a compatibility fallback.

## 7. Persistent identity rules

### Tunnel ID

- saved once during setup;
- treated as installation/profile identity;
- never replaced automatically;
- changing it requires an explicit user reconfiguration action;
- Desktop restart must not change it;
- tunnel-client restart must not change it;
- local MCP port change must not change it.

### Runtime alias

Default:

```text
lnwjud
```

The alias is local supervision state only. It can be rebuilt if needed while preserving the same `tunnel_id`.

### Runtime API key

- remains local;
- use DPAPI/protected secret storage;
- do not persist the literal key in Git, logs, argv examples, or plain profile metadata;
- rotation reconnects the same tunnel rather than creating a replacement tunnel.

## 8. Desktop startup flow

Proposed order:

```text
Desktop starts
   |
   +--> load settings / project state
   |
   +--> start application-global MCP HTTP listener
   |
   +--> obtain actual loopback /mcp URL
   |
   +--> TunnelRuntimeReconciler.start()
           |
           +--> validate tunnel-client
           +--> validate saved tunnel_id
           +--> validate protected key
           +--> reconcile local runtime alias
           +--> verify health/ready/poll health
```

The local MCP must start independently of tunnel health.

## 9. Reconnect policy

The runtime must retry for as long as the feature remains enabled. A temporary burst limit may slow retries, but must not permanently give up after five failures.

Recommended reconnect classes:

```text
Immediate retry class:
  process disappeared
  transient network failure
  429 / 5xx control-plane responses

Operator-action class:
  401 / 403
  missing/revoked runtime key
  tunnel_id invalid or inaccessible
  missing tunnel-client binary
  incompatible profile
```

Recommended transient backoff:

```text
1s -> 2s -> 4s -> 8s -> 15s -> 30s -> 60s max + jitter
```

After reaching the cap, keep retrying at the capped interval while showing `Reconnecting`; do not silently disable continuity.

## 10. Local MCP port changes

The Desktop MCP port may be dynamic. That is acceptable.

If Desktop restarts and receives a different loopback port:

```text
same tunnel_id
same runtime alias
new local mcp.server-url
```

The reconciler repairs/reconnects only the local target binding. ChatGPT's tunnel selection must remain untouched.

## 11. Tool/session continuity

There are two different promises:

### Connection/profile continuity

Expected v4.11 behavior:

- same ChatGPT tunnel configuration;
- no tunnel recreation;
- no manual edit of a connector URL;
- no manual reconnect merely because local tunnel-client restarted;
- same tool catalog when lnwjud version/schema did not change.

### Schema changes

If a future lnwjud upgrade actually changes MCP tool schemas, ChatGPT may still need its normal connector/tool metadata refresh behavior. v4.11 must not pretend a transport continuity feature can override client-side schema caching rules.

The acceptance test for v4.11 is specifically **reconnect with unchanged schema without manual refresh**.

## 12. Long-running work

Persistent tunnel identity and outcome-driven ChatGPT work are complementary. lnwjud must not impose an elapsed-time stop or append handoff instructions after a fixed number of minutes.

For commands that are naturally asynchronous, the durable path remains:

```text
long command / build / test / packaging
        |
        v
return durable task_id quickly
        |
        v
work continues locally
        |
        v
status/result calls until terminal
```

This is an execution primitive, not a scheduled end to the ChatGPT run. While the run remains active, ChatGPT keeps checking results and continues toward acceptance. A synchronous request may still have its own request deadline, but there is no lnwjud-wide 22/25/60-minute run cutoff.

## 13. Request correlation and replay

Official tunnel-client protocol already supplies an opaque `request_id` for each polled command and defines retry behavior for terminal response delivery.

Do **not** create a second distributed request protocol in v4.11.

Instead:

- preserve MCP JSON-RPC IDs normally;
- keep long execution durable and return handles early;
- add local request-ID diagnostic correlation if the official transport exposes it at a safe integration boundary;
- chaos-test disconnect after dispatch/response;
- only add a small local dedupe/receipt layer later if empirical tests prove duplicate command delivery can cause a local effect to be replayed.

No custom relay request journal is required for the initial v4.11 architecture.

## 18. Acceptance matrix

### A. tunnel-client process restart

1. ChatGPT is already configured to the tunnel.
2. Kill only tunnel-client.
3. lnwjud detects it and reconnects the same `tunnel_id`.
4. Next tool call works.
5. No connector reconfiguration.

### B. Desktop restart

1. Same ChatGPT conversation/tunnel configuration remains.
2. Exit lnwjud completely.
3. Reopen lnwjud.
4. Desktop MCP starts, possibly on a different local port.
5. Runtime reconciler attaches the same tunnel to the new local URL.
6. Next tool call works without changing tunnel ID.

### C. 10-second network outage

1. Disconnect network for 10 seconds.
2. Restore network.
3. tunnel-client/control-plane polling recovers automatically.
4. Same ChatGPT tunnel remains configured.

### D. 5-minute outage

Reconnect attempts continue at bounded backoff; runtime does not permanently give up.

### E. API key revoked

Do not tight-retry. Show `Auth required`. After saving a new runtime key, reconnect the same tunnel ID.

### F. local MCP port changes

Reconnect local binding only; remote tunnel identity stays unchanged.

### G. long background task

1. Start durable shell task.
2. Tunnel disconnects.
3. Task continues locally.
4. Tunnel reconnects.
5. Retrieve same task result.

### H. unchanged catalog

Restart Desktop/tunnel-client without changing lnwjud tool schema. The connector must continue without a manual refresh in the tested supported ChatGPT flow.

## 20. Definition of done

v4.11.0 is complete when:

- a user installs lnwjud locally and uses their own tunnel-client;
- user configures one existing OpenAI `tunnel_id` once;
- no VPS/domain/Cloudflare/lnwjud server is required;
- tunnel-client can die/restart and return to the same tunnel automatically;
- Desktop can restart and rebind the same tunnel to its new loopback MCP URL;
- short network outages recover automatically;
- transient failures do not permanently disable reconnect;
- auth failures ask for operator repair instead of looping;
- long local tasks survive tunnel loss through existing durable task handles;
- unchanged MCP schemas work again after reconnect without reconfiguring the ChatGPT tunnel;
- existing permission, recovery, Active Project, and Full/Balanced/Safe boundaries remain authoritative.

Final invariant:

> **One local installation, one OpenAI tunnel identity, reconnect forever until the user disables it.**
