# lnwjud v4.52.0 — Cross-Platform macOS + Linux Architecture & Delivery Plan

> Status: **Planning / implementation-ready**
> Date: **2026-09-02**
> Baseline tag: **`v4.52.0`**
> Baseline commit: **`a5e6c3e1ecce46c296d8712e28e0dd1d7e59ea36`**
> Working branch: **`feat/cross-platform-macos-linux-v4.52.0`**
> Scope of this document: **architecture + phased implementation plan only**. No macOS/Linux implementation is introduced by this planning change.

---

## 0. Executive summary

เป้าหมายของงานนี้คือทำให้ lnwjud ซึ่งปัจจุบันเป็น Windows-first Electron + MCP runtime สามารถใช้งานจริงบน **macOS** และ **Linux** โดยไม่ทำให้ความสามารถเดิมบน Windows ถอยหลัง ไม่ลด security boundary และไม่สร้าง code fork สามชุดที่ดูแลยากในระยะยาว

แนวทางหลักคือเปลี่ยนจากสถาปัตยกรรมที่หลายจุดเรียก Windows implementation โดยตรง ให้เป็น:

1. **platform-neutral core** — domain/application/security/storage/workspace/tool contracts ต้องไม่รู้จัก Windows, macOS หรือ Linux เกินกว่าข้อมูล platform metadata ที่เป็น abstraction
2. **platform contracts** — กำหนด contract สำหรับ data/config/cache paths, secret protection, process tree, startup, scheduler, native UI, capture, notifications, tunnel runtime, bundled binaries, updater และ platform diagnostics
3. **platform adapters/providers** — Windows adapter รักษาพฤติกรรมเดิม, macOS adapter ใช้ API/permission ของ macOS, Linux adapter แยก X11/Wayland/desktop-session capability ตามจริง
4. **capability truthfulness** — tool ที่ยังไม่มี provider บน platform นั้นต้องรายงาน `unsupported`, `dependency_missing`, `permission_required`, `session_unavailable` หรือ `provider_not_delivered` อย่างตรงไปตรงมา แทนการขึ้น internal error หรือชี้ให้ผู้ใช้ไปตั้งค่า Windows ที่ไม่มีอยู่
5. **native build per OS** — build/package/test บน runner ของระบบปฏิบัติการนั้นจริง ไม่ใช้ cross-compilation เป็น release authority สำหรับ native assets
6. **preserve exact-source release trust** — แนวทาง main CI → exact-SHA artifact → tag release ที่ใช้อยู่ต้องคงไว้ แต่ขยายเป็น Windows/macOS/Linux artifacts
7. **incremental delivery** — เริ่มจาก headless/core/MCP parity ก่อน แล้วค่อย desktop-native parity; Windows ต้อง green ทุก phase

สิ่งสำคัญ: งานนี้ **ไม่ควรทำเป็น “เพิ่ม mac/linux target ใน electron-builder แล้วแก้ error ทีละจุด”** เพราะ Windows coupling กระจายอยู่ใน data paths, DPAPI, process ownership, native capability bridge, WSL/registry/event logs, tunnel lifecycle, stdio launcher, updater, Doctor/Tools remediation, packaging resources และ CI/release contract

## 1.2 Reconciliation กับ historical v4.44.0 native macOS/Linux master plan

ใน repo มี master plan เก่าที่ `docs/superpowers/plans/2026-08-31-lnwjud-v4.44.0-native-macos-linux.md` ซึ่งมีประโยชน์เป็น **historical requirements checklist** แต่ไม่ใช่ implementation baseline ของงานนี้ เพราะโค้ดจริงเดินหน้ามาถึง `v4.52.0` แล้ว และ branch prototype เดิมไม่มี commit ที่อยู่ข้างหน้า release ปัจจุบัน

### สิ่งที่ carry forward จากแผน 4.44.0

- ใช้ **shared core + platform adapters/providers** ไม่สร้าง Windows/macOS/Linux fork แยกกัน
- จำกัด raw `process.platform` checks ให้อยู่ composition/platform boundary แทนการกระจายใน domain/application/storage/MCP
- รักษา Active Project, permission profile, Full Bypass, goal lease, destructive-scope, Recovery Trash/checkpoints และ approval semantics ให้เท่ากันทุก OS
- POSIX `/`, home root และ mount root ต้องไม่กลายเป็น trusted mutation scope โดยอัตโนมัติ
- process cancellation ต้องยืนยัน process identity/ownership และห้ามรายงาน cancelled แบบ optimistic; ถ้ายืนยันปลายทางไม่ได้ต้องคงสถานะเทียบเท่า `termination_unverified`
- macOS native layer ให้เริ่มจาก **Swift native host** ที่มี protocol จำกัด operation + integrity/version handshake
- Linux native layer ให้เริ่มจาก **Rust native host** เฉพาะส่วนที่ Node/Electron/DBus provider ทำไม่ได้ โดยห้าม setuid/privilege escalation
- Wayland computer-use/capture ต้องผ่าน user-approved portal/session ตาม security model ของ compositor; X11 capability ไม่ได้แปลว่า Wayland พร้อมเท่ากัน
- persisted secrets ต้อง fail closed เมื่อ secure provider ไม่พร้อม; ห้าม plaintext/basic-text fallback ใน production
- build/package/native acceptance ต้องรันบน target OS จริง และ release evidence ต้องผูก exact commit/artifact hash
- macOS signing/notarization และ Linux package/session acceptance เป็น release gate จริง ไม่ใช่ checklist เชิงเอกสาร

### สิ่งจากแผนเก่าที่ต้อง revalidate หรือแทนที่ตาม v4.52.0

- **STDIO launcher:** แผน 4.44.0 เคยเสนอให้เลิก private Node และใช้ packaged Electron `--mcp-stdio` โดยตรง แต่ `v4.52.0` มี design ใหม่ที่ตั้งใจใช้ private Node 24 + `lnwjud-mcp-stdio.cjs` เพื่อรักษา console/stdin/stdout pipe ownership ขณะที่ Secure Tunnel ใช้ Desktop loopback HTTP MCP ดังนั้น cross-platform port ต้อง **รักษา contract นี้ก่อน** ด้วย POSIX launcher + private Node target binary; การเปลี่ยนกลับไป Electron-hosted STDIO ต้องเป็น ADR แยกและมี packaged-host regression evidence
- **Secret/AV history:** แผนเก่ามี Issue/AV-specific assumptions หลายข้อ ให้ถือเป็น historical security evidence เท่านั้น งาน 4.52.0 ต้องตัดสินจาก source/runtime ปัจจุบันและ migration fixtures จริง ไม่ถือว่าสถานะ issue เดิมยังเหมือนเดิมโดยอัตโนมัติ
- **Office parity:** แผนเก่าเสนอ JXA/LibreOffice equivalents แต่ `office` ปัจจุบันมี semantics จาก Windows COM; v1 ของ cross-platform program นี้จะคง Windows-only อย่างตรงไปตรงมาก่อน เว้นแต่ schema/semantic review ยืนยันว่าการเพิ่ม provider ไม่ทำให้ contract เปลี่ยนความหมาย
- **Support floor:** macOS 13+ และ Ubuntu 24.04 LTS x64 จากแผนเก่าเป็น candidate ที่ดี แต่ Phase 0 ต้อง revalidate กับ Electron 43, Node 24, native dependencies, tunnel/runtime artifacts และ signing/package chain ของ 4.52.0 ก่อนประกาศ GA
- **Tool/runtime scope:** ใช้ inventory ของ 4.52.0 เป็นตัวจริง เพราะตั้งแต่ 4.44.0 มี OAuth/tunnel, Tools/Doctor, runtime/provider และ packaging behavior เปลี่ยนเพิ่มหลายจุด

หลักการคือ **carry forward invariants, discard stale implementation assumptions** และตัดสินจาก code/config/tests ของ `v4.52.0` ทุกครั้ง

## 1.3 Current architecture ที่ควรรักษา

จาก `docs/architecture/ARCHITECTURE.md` โครงสร้างที่ดีและควรรักษาไว้คือ dependency direction:

```text

main -> application -> domain -> ports/interfaces
adapters -> ports/interfaces
mcp-server -> application
Desktop IPC -> application
CLI -> application
```

หลักการเดิมที่ต้องรักษา:

- `domain` และ `application` ไม่ import Electron / React / concrete SQLite / concrete MCP transport
- authorization, workspace scope, recovery/checkpoint, audit และ explicit confirmation ต้องเป็น centralized policy ไม่ใช่กระจายไปตาม UI
- process execution ต้องเป็น argv-based และรักษา ownership/cancellation semantics
- MCP tool schema เป็น public runtime contract; platform adaptation ห้ามทำ schema เปลี่ยนแบบเงียบ ๆ

# 2. Goals, non-goals, invariants

## 2.1 Primary goals

1. lnwjud Desktop เปิดและใช้งาน core workflow ได้บน Windows, macOS และ Linux
2. Local MCP / stdio runtime ใช้งานได้โดยไม่ต้องติดตั้ง system Node.js
3. Secure Tunnel + OAuth/session continuity ใช้ได้ทุก supported desktop OS เมื่อ upstream tunnel runtime มี binary สำหรับ target นั้น
4. Active Project, Permission v2, Full Bypass semantics, Recovery Trash/checkpoint, goal lease, scheduled continuation และ audit behavior ต้องไม่แตกต่างโดยไม่มีเหตุผลด้าน platform
5. Core tools เช่น file/search/git/process/project/MCP/context/goals ใช้งานได้บนทุก Tier-1 platform
6. Native tools มี provider matrix ที่ชัดเจนและ Doctor รายงานสาเหตุจริง
7. package/release มี checksum, provenance, exact-SHA source binding และ update metadata แยก platform
8. Windows v4.52 behavior เป็น regression baseline; cross-platform refactor ต้องไม่บังคับ rewrite Windows implementation แบบ big bang

## 2.2 Explicit non-goals ของระยะแรก

- ไม่ทำให้ `wsl_exec` / `wsl_fs` ใช้บน macOS/Linux เพราะชื่อและ contract คือ WSL
- ไม่เปลี่ยน Windows Registry/Event Log semantics ให้เป็น launchd/journalctl โดยใช้ชื่อเดิมถ้า schema ไม่เทียบเท่า
- ไม่อ้างว่า Microsoft Office COM parity บน macOS/Linux; provider อื่นต้องผ่าน contract/semantic review ก่อน
- ไม่รับรองทุก Linux distro/compositor ในวันแรก
- ไม่รับรอง Linux Wayland raw input/control หากไม่มี safe provider ที่ระบบอนุญาต
- ไม่ใช้ plaintext fallback สำหรับ API key/OAuth session เพียงเพื่อให้ Linux headless “ทำงานได้”
- ไม่ merge native prototype ที่เก่าโดยอัตโนมัติ
- ไม่เปิด auto-update ของ package format ใดจน behavior ของ install/update/rollback ผ่าน acceptance test จริง

## 2.3 Security invariants ห้ามลด

- no shell-string execution สำหรับ user-controlled command เมื่อ argv API ทำได้
- canonical path + realpath/symlink escape checks ต้องคงอยู่
- user confirmation / permission profile / Full Bypass semantics ต้องมาจาก shared policy
- credentials ต้องไม่อยู่ command line, logs, telemetry, profile plaintext หรือ crash report
- process kill ต้องพิสูจน์ ownership ก่อน terminate tree
- packaged helper/binary ต้องมี integrity/provenance policy
- native permission denial ต้อง fail closed
- unsupported provider ต้องไม่ silently fallback ไป provider ที่ scope/permission อ่อนกว่า
- release ต้องใช้ artifacts ที่ผูกกับ exact source SHA

# 4. Proposed architecture

## 4.1 High-level architecture

```text
┌────────────────────────────────────────────────────────────┐
│ Renderer / CLI / MCP transports                            │
├────────────────────────────────────────────────────────────┤
│ Application + Domain + Permission + Audit + Goal runtime   │
├────────────────────────────────────────────────────────────┤
│ Existing service ports / capability contracts              │
├────────────────────────────────────────────────────────────┤
│ Cross-platform runtime composition                         │
│   PlatformContext + PlatformPaths + ProviderRegistry       │
├───────────────┬──────────────────┬─────────────────────────┤
│ Windows       │ macOS            │ Linux                   │
│ adapters      │ adapters         │ adapters                │
│ DPAPI/UIA/... │ Keychain/AX/...  │ SecretSvc/AT-SPI/...    │
├───────────────┴──────────────────┴─────────────────────────┤
│ OS / Electron / browser / native helpers / system tools    │
└────────────────────────────────────────────────────────────┘
```

## 4.3 Core contracts

### `PlatformContext`

```ts
interface PlatformContext {
  readonly os: 'windows' | 'macos' | 'linux';
  readonly nodePlatform: NodeJS.Platform;
  readonly arch: 'x64' | 'arm64';
  readonly targetTriple: string;
  readonly isPackaged: boolean;
  readonly desktopSession?: 'windows' | 'aqua' | 'x11' | 'wayland' | 'headless';
}
```

Responsibilities:

- normalize platform naming once
- prevent dozens of raw `process.platform === ...` branches across business code
- expose session/compositor only as capability metadata, not policy shortcuts

### `PlatformPaths`

Must expose separate semantic roots:

- `dataDir`
- `configDir`
- `cacheDir`
- `logsDir`
- `runtimeDir`
- `credentialsMetadataDir` (metadata only; secret material may live in keyring)
- `tunnelProfileDir`
- `backgroundTaskDir`
- `browserProfileDir`

Candidate mapping:

| Semantic path | Windows | macOS | Linux |
|---|---|---|---|
| data/config compatibility | `%APPDATA%/lnwjud` | `~/Library/Application Support/lnwjud` | `$XDG_DATA_HOME/lnwjud` or `~/.local/share/lnwjud` |
| config future | same legacy root initially | Application Support | `$XDG_CONFIG_HOME/lnwjud` |
| cache | local app cache | `~/Library/Caches/lnwjud` | `$XDG_CACHE_HOME/lnwjud` |
| runtime locks | data/runtime initially | Application Support/runtime or temp-safe root | `$XDG_RUNTIME_DIR/lnwjud` when available, otherwise protected data/runtime |

Migration rule:

- Windows path must stay backward compatible
- v1 mac/Linux should avoid moving files between XDG roots repeatedly; freeze layout before public release
- every path override from environment must be normalized and scope-tested

### `SecretStore`

```ts
interface SecretStore {
  readonly providerId: string;
  status(): Promise<SecretStoreStatus>;
  set(ref: SecretRef, value: Uint8Array): Promise<void>;
  get(ref: SecretRef): Promise<Uint8Array | null>;
  delete(ref: SecretRef): Promise<void>;
}
```

Providers:

- Windows: existing DPAPI-compatible provider
- macOS: Keychain-backed provider
- Linux desktop: Secret Service/libsecret-backed provider
- Linux headless: explicit configured secure provider or environment-injected master key; **no automatic plaintext fallback**

Secret payload/file format must carry version/provider metadata so migration is explicit:

```text
lnwjud-secret:v3:<provider-id>:<reference-or-envelope>
```

Never silently reinterpret an existing DPAPI payload on another OS.

### `ProcessPlatform`

Responsibilities:

- executable resolution semantics
- wrapper requirement (`.cmd`/`.bat` on Windows only)
- detached/process-group creation
- child start identity
- process tree inspection
- graceful terminate and force terminate
- owned-process verification

POSIX strategy:

- create dedicated process group/session for managed child where safe
- first `SIGTERM`
- bounded wait
- `SIGKILL` only after ownership revalidation
- do not kill arbitrary negative PGID unless group ownership was created/recorded by lnwjud

### `BundledToolProvider`

Resolves assets by target triple rather than hard-coded `.exe`:

```text
windows-x64
macos-arm64
macos-x64
linux-x64
linux-arm64
```

Each bundled tool manifest entry:

- logical name
- version
- target triple
- packaged relative path
- SHA-256
- source URL/license metadata
- required/optional
- invocation/version-probe contract

Examples: Node runtime, ripgrep, tunnel-client, ngrok/cloudflared if bundled, PDF provider, OCR/native helpers, ffmpeg when chosen.

### `CapabilityProviderRegistry`

A capability must expose availability separate from execute:

```ts
type CapabilityState =
  | 'ready'
  | 'permission_required'
  | 'dependency_missing'
  | 'provider_not_delivered'
  | 'platform_unsupported'
  | 'session_unsupported'
  | 'temporarily_unavailable';
```

This state becomes single source for:

- MCP tool failure reason
- Tools page status
- Doctor issue
- remediation UI
- telemetry/health summary

# 5. Tool/capability portability model

# 6. Filesystem and workspace architecture

## 6.1 Replace Windows drive-root assumptions

`packages/workspace/src/machine-root.ts` currently models machine root as `C:\`, `D:\`, etc.

Target concepts:

```ts
interface FilesystemRootDescriptor {
  readonly path: string;
  readonly caseSensitivity: 'sensitive' | 'insensitive' | 'unknown';
  readonly kind: 'volume-root' | 'filesystem-root' | 'workspace-root';
}
```

Rules:

- Windows can preserve drive-root compatibility
- POSIX filesystem root is `/`, but unrestricted machine-root access must **not** automatically mean entire `/` is registered/authorized
- Active Project remains primary scope
- legacy machine-root workspace semantics must be reviewed so registration does not accidentally broaden permission on POSIX

## 6.2 Canonical-path behavior

Test all of:

- POSIX symlinks
- Windows junctions/reparse points
- macOS case-insensitive APFS default
- case-sensitive APFS volume
- Linux case-sensitive filesystems
- Unicode normalization edge cases on macOS
- deleted/recreated parent path race
- cross-volume move behavior

Path comparison must use a platform-aware canonicalization service rather than `.toLowerCase()` everywhere.

## 6.3 Recovery Trash / checkpoints

- storage model remains shared
- payload paths must use semantic data root
- restore must never overwrite a different inode/target after symlink swap
- file permissions on POSIX restore must be intentionally preserved or documented
- executable bit preservation must be covered for scripts/launchers

# 7. Process execution and durable task architecture

## 7.1 Refactor ownership

Move `ProcessTreeTerminator` interface out of `windows-process-tree.ts` into neutral module, e.g.:

```text
packages/process/src/process-tree.ts
packages/process/src/platform/windows-process-tree.ts
packages/process/src/platform/posix-process-tree.ts
packages/process/src/platform/spawn-invocation.ts
```

`ProcessManager` must depend on interface/factory, not `new WindowsProcessTree()`.

## 7.2 Spawn semantics

Windows:

- preserve `.cmd/.bat` ComSpec handling
- preserve `windowsHide`
- preserve taskkill tree behavior and existing guardrails

POSIX:

- executable + argv directly
- no implicit `/bin/sh -c`
- capture `pid`, process group and start identity
- managed background process may use dedicated process group
- cancellation first graceful signal, then forced termination after bounded wait

## 7.3 Environment policy

Current environment allowlist is Windows-oriented. Split into:

Shared minimum:

- `PATH`
- `HOME`
- locale variables as required
- TLS/certificate variables only if policy permits

Windows-specific:

- `PATHEXT`, `SYSTEMROOT`, `WINDIR`, `TEMP`, `TMP`, `USERPROFILE`, etc.

POSIX-specific:

- `SHELL` should not imply shell execution
- `TMPDIR`
- `XDG_*`
- `DISPLAY`, `WAYLAND_DISPLAY`, `DBUS_SESSION_BUS_ADDRESS` only for providers that need desktop session and only after policy review

Secrets remain excluded unless explicitly injected through a guarded secret/environment contract.

## 7.4 Durable shell tasks

Persist platform-neutral metadata:

- executable
- argv
- cwd
- managed PID
- process-group metadata where applicable
- start identity
- stdout/stderr capture paths
- cancellation policy

Do not persist volatile OS handle objects.

Acceptance:

- restart-safe status lookup
- orphan detection
- no accidental kill of PID-reused unrelated process
- same goal/task semantics on all OS

# 12. Native capability implementation strategy

## 12.1 macOS native adapter choices

Must run a technical spike before freezing implementation language.

Candidate mechanisms:

- Accessibility: AX API via Swift/native helper or maintained native binding
- input: CGEvent with permission checks
- capture: ScreenCaptureKit where feasible
- window metadata: CGWindow + AX
- OCR: Vision framework
- audio: AVFoundation or a tightly controlled ffmpeg/native provider

Preferred architecture:

```text
native/macos-host/
  Swift package / executable
  one versioned JSON-over-stdio protocol
```

Benefits:

- native permissions and APIs stay outside Electron main logic
- same integrity/version handshake pattern as Windows helper
- crash isolation
- easier notarization/entitlement review

Bridge contract must be versioned and bounded; do not send arbitrary shell commands through bridge.

## 12.2 Linux adapter choices

Avoid one giant privileged binary.

Preferred native boundary from the historical design is a small Rust host, only for operations that cannot be delivered safely/reliably by Node/Electron/DBus directly:

```text
native/linux-host/
  Cargo.toml
  Cargo.lock
  src/
    main.rs
    protocol.rs
    atspi.rs
    x11.rs
    portals.rs
    media.rs
```

Rules:

- no setuid, no root daemon, no implicit sudo/pkexec
- pinned `Cargo.lock` and dependency/license/SBOM evidence for release
- JSON-over-stdio protocol follows the same bounded operation/version/integrity model as the macOS host
- do not route simple `/proc`, filesystem, HTTP, or ordinary process work through the native host merely for uniformity

Possible providers:

- system info/process: Node + `/proc` bounded parser
- accessibility: AT-SPI2 over DBus
- screenshot/screen record on Wayland: xdg-desktop-portal + PipeWire
- X11: dedicated X11 provider where needed
- notification: DBus/freedesktop or Electron
- clipboard: desktop APIs/provider based on session

Provider registry must select by session and return truthful readiness.

## 12.3 Native helper protocol rules

For every helper:

- semantic operation allowlist
- strict JSON schema
- input size limits
- no arbitrary process execution
- absolute path operations pass through main security policy first
- stdout reserved for protocol; stderr bounded diagnostics
- helper binary hash/version verified in packaged builds
- helper timeout/cancellation behavior tested

# 18. Migration and backward compatibility

## 18.1 Windows data

- no forced data root migration in first cross-platform release
- existing SQLite DB, checkpoints, settings and tunnel profile remain readable
- DPAPI secret format remains supported on Windows

## 18.2 Cross-OS data copy

A copied Windows data directory on macOS/Linux:

- non-secret portable DB/settings may be migrated after schema validation
- DPAPI secret cannot be decrypted; UI must request re-auth/re-pair while retaining non-secret data
- never mark DPAPI ciphertext as corrupt and delete it automatically

## 18.3 Tunnel profile migration

Profile may reference Windows `.cmd` path.

On another OS:

- detect incompatible launcher path
- rewrite only the launcher field that lnwjud owns
- preserve user profile fields
- create backup/checkpoint before mutation

## 18.4 Settings schema

Add platform-specific settings only under namespaced/optional fields; avoid making Windows settings mandatory on other OS.

## 18.5 Cross-host backup / restore

Backup portability must be explicit rather than assuming a Windows snapshot can be restored byte-for-byte on another OS.

- add source platform/arch/data-schema/provider metadata to backup manifest
- portable DB/settings/history/log metadata may migrate after schema validation
- host-bound secret envelopes/Keychain/Secret Service/DPAPI references are not transplanted as if decryptable; preserve evidence and require re-auth only for the affected secret
- foreign absolute workspace paths stay recorded but unavailable until the user relinks them; never rewrite `C:\\...` into `/...` or vice versa heuristically
- same-host restore remains backward compatible and is the regression baseline
- cross-host restore must be atomic, resumable and rollback-safe, with a receipt listing what migrated, what was relinked, and what requires re-auth

# 23. Risk register

| Risk | Severity | Why | Mitigation |
|---|---:|---|---|
| Wayland blocks synthetic input/window control | High | compositor security model | explicit session capability matrix; portal-first; no unsafe fake parity |
| Linux Secret Service unavailable/headless | High | no desktop keyring session | fail closed + explicit secure env/master-key mode |
| macOS TCC permissions differ dev vs signed build | High | unsigned tests misleading | signed/notarized acceptance gate |
| Node/Electron native dependency lacks target prebuild | High | package cannot boot | Phase 0/packaging dependency audit; native runner rebuild |
| process kill semantics kill unrelated PID | Critical | destructive | start identity + ownership + process-group ledger |

| tunnel client missing target binary | High | remote MCP unavailable | target manifest readiness gate; truthful unavailable state |

# 24. Decision gates that must be closed before corresponding implementation

## Gate A — Minimum supported versions

Freeze after validating:

- Electron 43 support
- Node/private runtime availability
- native dependency ABI
- signing/notarization requirements

## Gate B — Linux input/Wayland promise

Choose one:

- Tier-1 Linux core + capture, input limited by session
- or require a provider that demonstrably works under target Wayland compositors

Do not advertise “full computer use” generically before Gate B.

## Gate C — Secret provider

Must select secure mac/Linux implementation and headless behavior before Tunnel/OAuth phase.

## Gate D — native helper technology

Freeze **Swift native host for macOS** and **Rust native host for Linux** plus the shared bounded protocol/integrity rules before implementation. A later provider may avoid the native host for an operation that Electron/Node/DBus can implement safely, but must not introduce a second arbitrary-command bridge or weaker authorization path.

## Gate E — package formats/updater

Freeze initial formats before CI/release work.

## Gate F — bundled third-party binaries

For each binary record:

- upstream source
- version
- license
- checksum
- target architecture
- update policy

# 30. Final architecture principle

The target is **one lnwjud product, one public tool contract, one security model, and multiple truthful platform providers**.

Do not build three products named lnwjud.

The desired end state is:

```text
same application/domain/security/tool contracts
                 +
         platform-aware composition
                 +
     native provider per supported OS
                 =
 Windows + macOS + Linux without policy drift
```

Whenever exact parity is impossible because the operating system intentionally restricts an operation, lnwjud should report that limitation clearly instead of weakening the OS boundary or pretending the tool is ready.
