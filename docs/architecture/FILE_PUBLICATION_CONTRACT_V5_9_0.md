# File publication and durability contract (lnwjud v5.9.0 candidate, Issue #219)

**Status:** Documentation of the current implementation, not a new durability API. v5.9.0 is not yet published; v5.8.7 remains the published baseline. The implementation may be reviewed again before v5.9.0 ships. This contract concerns calls mediated by the lnwjud Gateway, not independent processes or third-party filesystem writers.

The labels below mean **SUPPORTED** (implemented within the stated scope), **UNSUPPORTED** (not furnished by this API), and **UNKNOWN** (not established for the specified host/filesystem or failure). Atomic pathname *publication*, byte persistence, writer-descriptor identity, and proof of crash recovery are separate properties.

| Capability / question | v5.9.0 candidate status | Precise scope |
| --- | --- | --- |
| Strict destination create-only | **SUPPORTED, conditional on filesystem support** | `write_file` with `mode: "create_new"` or `overwriteExisting: false` stages a unique temporary file in the destination directory, then uses `link(temp, destination)`. Existing targets yield `CONFLICT` on `EEXIST`, including with the Full permission profile. A concurrent creator cannot be overwritten by this no-replace link. If the filesystem does not support the link operation, the call fails rather than falling back to replacement. |
| One final pathname and temporary-file staging | **SUPPORTED** | The implementation creates a sibling `.<basename>.<uuid>.tmp` with `wx`, hard-links it into the final pathname for strict create-only, then attempts to unlink the temporary entry. The final pathname is the requested target; **one physical file creation / no intermediate directory entries is not guaranteed**. The temporary entry and final entry briefly refer to the same inode where hard links are supported. Cleanup errors are deliberately swallowed; a temporary entry may survive. The parent directory may also have been created. |
| Same-process writer descriptor and ordered identity receipt | **UNSUPPORTED** | `write_file` does not return `st_dev`/`st_ino` samples before write, after write, or after file sync. It does not expose its writer file descriptor, the final descriptor identity, an externally retrievable ordered journal, or a native receipt attesting that a particular process/descriptor performed every step. A subsequent `stat` or read is a new observation, not a writer-owned ordered receipt. |
| File `fsync` and parent-directory `fsync` | **UNSUPPORTED** | `AtomicFileWriter` uses Node `writeFile`, `link` or `rename`, and cleanup `unlink`; it does **not** explicitly call file-descriptor `sync`/`datasync`, request `writeFile({ flush: true })`, or `fsync` the parent directory. A successful `write_file` reports completed API operations, **not crash/power-loss durability**. No per-step sync status or error is returned. |
| macOS exFAT strict create-only/link and crash durability | **UNKNOWN for the target filesystem** | No macOS exFAT-specific acceptance or filesystem persistence guarantee is established by this API. Hard-link support and sync durability must be established for that exact platform, mount, and filesystem; do not assume that a tested APFS/NTFS/Linux path applies. Unsupported link operations fail closed; there is no automatic rename fallback in create-only mode. |
| Overwrite behavior without explicit create-only | **SUPPORTED with permissions** | Non-create-only publication uses `rename(temp, destination)`; an existing target is subject to the FileService profile, authorization, confirmation, path guards, and recovery/checkpoint rules. This is **not** strict no-replace. Full permission profile can allow the legacy replacement path when strict create-only was not requested. |
| Successful `write_file` response | **SUPPORTED (limited)** | The successful service result returns `path`, UTF-8 `bytesWritten`, and optional overwrite `checkpointId`. It is **not** an inode, fsync, native terminal, or durable storage receipt. |
| Bounded ordered failure receipt / retrieval after worker death, response truncation, or transport loss | **UNSUPPORTED** | `write_file` has no dedicated persisted attempt ID, publication state machine, durable writer-side acknowledgement, or read-back endpoint. An observed pre-dispatch rejection describes only that invocation's decision. A transport failure or process death around link/rename leaves final-target creation **UNKNOWN** to the caller until independently inspected, and a later inspection still does not prove writer ownership or filesystem durability. Do not automatically replay a possibly published operation. |
| Distinct `FILE_NOT_CREATED` / `FILE_CREATED_BUT_UNVERIFIED` / unknown-creation receipts | **UNSUPPORTED** | These are **not** guaranteed named result states of `write_file`. A preflight rejection may establish that this invocation did not dispatch a write; `CONFLICT` can establish no overwrite, not which actor created the existing target. After ambiguous dispatch, label the outcome **UNKNOWN**, preserve the relevant admission/approval boundaries, and investigate without a blind retry. |
| Single read-only exact installed build + effective file-publication contract + permission profile attestation | **UNSUPPORTED** | There is no one read-only command returning the running binary's exact build digest *and* effective `write_file` contract/policy. `tool_describe` can expose the current ToolRegistry's `appVersion` and input-schema SHA-256, which are **not** proof of installed binary identity. `permission_profile` can inspect the configured profile separately. `installed_runtime_context` reports dependent runtimes, **not** an attested lnwjud binary identity. When necessary, verify installed binary/package identity separately against signed release provenance. |
| Launch a separately reviewed native publisher through `shell` / `process_start` | **SUPPORTED only as ordinary authorized process dispatch** | An approved executable may be launched if it passes the current platform, scope, command policy, ownership, Host Approval, and process containment requirements. That **does not** upgrade `write_file` with native receipt/fsync guarantees, and does not imply a particular publisher is approved or supported. The publisher must implement and independently validate its own receipt, descriptor, durability, crash-recovery and filesystem-specific contract. On macOS v5.9.0 candidate, managed writers and durable shell are deliberately fail-closed pending Issue #216's OS-enforced owner-loss containment: their normal dispatch cannot be assumed available. |
| `task_create` as a direct native file-publication API | **UNSUPPORTED** | `task_create` is an app-owned task/scheduling operation, not a built-in same-descriptor native file publisher. A scheduled shell payload, where supported, re-enters the same execution/authorization controls and supplies no additional file receipt guarantee. |
| Full profile / Full Bypass and script restrictions | **SUPPORTED permission semantics; native publisher acceptance UNKNOWN** | Full profile relaxes ordinary application prompts but does not override an explicit `create_new` no-replace contract. Full Bypass (when intentionally enabled) can skip lnwjud application prompt/profile/command/scope controls, but not schema validation, native OS filesystem limitations, process-lifetime fencing, provider failures or receipt requirements. It is **not** a recommended bypass for unsafe source-editing scripts or unsupported publication; a separately reviewed dedicated tool/executable is required if the intended guarantee cannot be established by the ordinary executable policy. |

## Operational interpretation

1. For ordinary UTF-8 text file creation, call `write_file` with `mode: "create_new"` (or `overwriteExisting: false`) and a valid writer/Goal lease when required. Treat this as **atomic target no-replace**, not single-inode-creation history, crash durability, or a native writer-attested receipt.
2. If the operation is denied before dispatch, retain the denial; if a destination collision is reported, do not replace the existing file. If the response is missing after possible dispatch, mark the result **UNKNOWN** and do not automatically repeat the write. Read-only inspection can help decide next steps but does not manufacture ordered native proof.
3. Workflows that require one open writer descriptor, ordered `st_dev/st_ino` values, file+directory `fsync` with surfaced errors, and lossless crash acknowledgements must use **a separately specified, reviewed and platform-validated native publication implementation**. Neither `write_file` nor standard `shell` alone attest those properties.
