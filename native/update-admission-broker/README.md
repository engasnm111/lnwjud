# Windows update admission broker core

This directory implements an isolated native admission state machine and Windows journal store. The production executable without arguments exits with `MAINTENANCE_REGISTRY_UNCONFIGURED` and code 125. The `service` argument enters an SCM-only dispatcher: it refuses a console launch, requires the genuine LocalService plus enabled service SID, checks the existing protected journal, and **always reports SERVICE_STOPPED with service-specific error 125**. It never reports SERVICE_RUNNING. Create-only, elevated image staging, SCM registration, protected parent and root directory provisioning commands now exist; none starts the service, creates a journal baseline, enrolls any trust authority or enables update execution. No authenticated command endpoint, production installer, executor or signalling operation exists; the broker is not packaged into the application. Automatic updates remain unavailable.

The selected deployment is a dedicated LocalService process with unrestricted `NT SERVICE\LnwjudUpdateAdmission` service SID. The service SID must own the root and new files explicitly. Shared LocalService ownership is refused by the store's exact owner check. The store grants full access only to its owner, SYSTEM and Administrators. The fixed domain is `lnwjud-windows-maintenance-v1`. The intended binary location is `ProgramFiles/Common Files/lnwjud/UpdateAdmission/v1`, with a protected store at `CommonAppData/lnwjud/update-admission`. Both must survive application replacement. The first automatic update must not replace this broker.

## Attended SCM registration (staging only)

The new `stage-image <source-path> <64-character SHA-256>` command is elevated, create-only and verifies the source bytes against the supplied digest **before** creating protected Common Files directories. It rejects empty or oversized (>128 MiB) images and creates a protected temporary image with explicit SYSTEM/Administrators ownership permissions, rechecks the copied bytes, atomically renames to the fixed image name without overwriting an existing image, and verifies the final path and digest. A failed stage attempts to clean only its own temporary/final image and refuses uncertain cleanup; empty protected directories may remain. It does not authenticate the supplied digest or provision any service. No actual elevated staging E2E has been performed. The `provision-service <64-character SHA-256>` executable command is **not** a self-install or a trust enrollment. It requires an elevated Administrator token, a pre-existing image at the fixed Common Files path with protected owners/DACLs and no reparse components or executable hard links, and an exact SHA-256 match. The supplied digest must come from a separately authenticated installation source; a caller-provided hash by itself does not prove origin or signature. The command creates the service **only if its name does not already exist**, initially disabled, configures LocalService with unrestricted service SID, sets a protected service-object DACL and requires a trusted SYSTEM/Administrators owner on SCM readback, switches to the required automatic-start registration only after those protections are applied, then re-queries SCM configuration and the image filesystem and rechecks the image hash. It never modifies a pre-existing service, starts the new service, initializes the journal, or installs application bytes. If post-creation validation fails it requests deletion; failure to delete is reported as an uncertain rollback, not success. Do not invoke this staging command on an end-user machine until an authenticated image enrollment path exists. No attended provisioning E2E has been accepted.

An attended elevated `provision-store-parent` command can now create the immediate `CommonAppData/lnwjud` parent with a protected Administrators-owned DACL, SYSTEM/Administrators full control and the service SID limited to traversal and child-directory creation. It refuses an unsafe existing parent and a ProgramData base granting unprivileged delete/ACL/ownership rights; new parents use atomic `CreateDirectoryW` with an explicit protected descriptor so a racing pre-created directory cannot be adopted or re-ACL'd, and the parent is verified by handle after creation. The SCM service must already exist so its service SID resolves. It does **not** create the journal root, initialize a baseline, authenticate a signer or enable updates. This command has not passed an elevated installed E2E and must not be run on a production machine before trusted installer enrollment.

The separate elevated `provision-store-root` command is create-only and requires the existing SCM registration, protected broker image, and verified `CommonAppData/lnwjud` parent. It creates `update-admission` with an explicitly protected service-SID owner and DACL granting full control only to that SID, SYSTEM, and Administrators. A narrowly scoped `SeRestorePrivilege` enable/restore permits an elevated administrator to assign the service SID as owner; missing privilege or uncertain restoration refuses. It uses atomic Windows `CreateDirectoryW` with a supplied security descriptor, so a pre-existing root is never adopted, overwritten, or repaired. It reopens the created root by handle to verify owner/DACL, then revalidates the parent and ProgramData base. A failed readback does not delete an unverified object. This command **does not** create `owner.lock`, a journal baseline, authenticated source authority, or an updater permit; it is not trust enrollment. A local non-elevated fixture tests root ACL construction and create-only behavior, **not** elevated service-SID installed provisioning. Do not run on a production machine before trusted installer enrollment.

The SCM bootstrap now performs a **read-only registration-shape check** before opening the native store. It queries the actual service configuration and requires the exact quoted fixed image path under `Common Files/lnwjud/UpdateAdmission/v1`, the `service` argument, own-process service type, automatic start, normal error control, no load-order group, dependencies or service tag, the `NT AUTHORITY\\LocalService` account, and an unrestricted service SID. Missing/inaccessible or mismatched SCM records fail closed. It also reads the service object's DACL and refuses an unprivileged owner or any allow ACE granting service configuration, control, deletion, ownership or DACL-write rights to identities other than SYSTEM or Administrators. Read-only access remains permitted. Missing or unreadable service security descriptors fail closed. The bootstrap also refuses configured SCM failure/recovery commands or actions, non-crash failure actions, delayed auto-start, triggers, required-privilege overrides and protected-launch overrides; it queries these extended SCM records directly rather than trusting a caller-supplied configuration. This prevents a service with a matching binary path but an alternate SCM command-execution or activation path from being accepted. The bootstrap additionally opens every filesystem component from the drive's Program Files directory through the fixed broker image without following reparse points, checks for unprivileged write/delete/ACL-modification rights and untrusted owners, and rejects a hard-linked executable. It never repairs or provisions those paths. These read-only ACL and file-shape checks do **not** authenticate executable bytes, a release signer, protected installation provenance or service provisioning; they cannot grant updater authority. Independently authenticated image provenance remains mandatory before the service may report ready.

## Implemented behavior

`AdmissionProtocol` accepts bounded strict UTF-8 JSON, rejects duplicate decoded field names and unknown fields/commands, and represents generation/revision as canonical unsigned decimal strings. Decoding requests does not grant authority or dispatch operations. There is no serialized proof flag.

`Enter` and `Promote` distinguish a newly granted permit from an existing held permit that requires reconciliation; only the new-grant result may initiate new work. A retry does not prove that an earlier side effect did or did not run. Promotion records now persist the exact parent permit ID, reject retries naming a different parent, and preserve that binding across restart; a matching retry still requires reconciliation. The future dispatcher must bind work identity and reconcile execution before retrying; this result alone does not provide exactly-once effects.

The updated permit journal requires a `parent` field for every record (empty for non-job permits); pre-change journals without this field fail closed. No automatic migration or production enrollment is provided.

`AdmissionCore` serializes admission and closure through one owner. It publishes each accepted mutation before acknowledging it. Registered runtime identities can acquire startup, call or background permits while open. A live parent permit can promote work to a native job permit during closure, so a request already admitted cannot disappear from the drain while spawning background work. Settlement requires a private proof capability. Native job settlement requires the distinct job-zero-and-reservation-released proof type. Ordinary operation settlement cannot release a job.

Closing blocks new work and requires every retained participant to prove quiescence for the new closure epoch, even if it was quiescent before the closure. A late runtime is quarantined. Sealing requires zero held permits and every registered active runtime quiescent. Quiescence proofs bind the participant and closure epoch. The drain receipt binds the fixed domain, epoch, transaction, generation, revision and journal digest. Consumers must revalidate its current position before effects; the receipt alone is not an install capability. Owner recovery requires cessation evidence, increments the generation, preserves closure and invalidates an earlier seal. Reopening requires a matching accepted-disposition proof after sealing. Timeouts never reopen admission. Completed transaction IDs remain as replay tombstones.

This correction applies when a new closure starts; an existing `closing` or `sealed` journal created by older code has not been repaired or independently validated. Production enrollment must not adopt such a journal as proof of current-epoch quiescence.

Each participant has a persistent monotonically issued sequence and contiguous settlement watermark. Permit IDs combine that participant's random ID and sequence. A retry cannot regrant a sequence at or below the watermark. Authenticated out-of-order settlements remain as records until every predecessor settles; then contiguous records compact into the watermark. Neither a held nor an unknown predecessor is discarded. Retirement removes a participant only after quiescence, complete settlement and separate native process-cessation proof. It revokes the in-memory principal. Future production peer capture must query and retain the actual live process identity for every request, so a stopped process can never mint a new principal. Old participant IDs remain invalid after retirement and restart.

`AdmissionStore` pins each existing directory without following reparses. For the installed service identity it also requires the immediate `CommonAppData/lnwjud` parent to have a protected DACL and SYSTEM/Administrators owner, rejecting unprivileged write/delete/ACL rights; the service SID may receive only child-directory creation rights there. This is necessary because the observed `C:\\ProgramData` parent permits ordinary Users to create new children. The check does not provision that parent, remove a hostile pre-created directory, or establish a trusted initial journal. The store retains a native byte-zero lock for its lifetime, rejects unsafe owner/DACL, reparses, hard links and oversized files, and creates lock/stage files with an explicit owner and protected DACL. It does not create missing roots or repair existing permissions. Missing current state always refuses, including after a previously closed journal is lost. Production has no bootstrap operation. The attended parent/root provisioners now stage protected directories only; they do not authenticate or create a baseline. A future trusted installer must authenticate a genuinely fresh baseline before its first snapshot. Publication flushes a pending file created with `CREATE_NEW`, checks the predecessor digest, replaces the current snapshot with write-through requested, and checks published file identity and digest. Pending publication makes ordinary open refuse. Recovery retains both files and refuses even a matching successor because the snapshot does not retain independently verifiable authority for its transition. A future authenticated recovery path must revalidate that authority without discarding held work. An uncertain publication poisons the current core instance. These are process-interruption guarantees; physical power-loss/filesystem recovery has not been accepted.

A recoverable intent must bind the exact transition, predecessor, revision, actor and evidence references to a protected broker authority, then revalidate evidence that can become stale. Authentication of a snapshot does not itself prove Job termination, owner cessation or application health; restoring an older authenticated journal pair also requires an independent freshness anchor. A machine-wide DPAPI scope by itself is not a service-specific key boundary. The existing containment service `inspect` path can reconcile and release a reservation, so it is not a read-only evidence API. Missing authority, an unavailable evidence issuer or an unverified freshness anchor must retain the pending hold.

The bounded store allows at most 128 simultaneous participants and 512 unsettled or out-of-order permit records. Sequential settled work and retired participants do not consume those lifetime limits. It retains at most 256 completed updater transactions, then refuses further updates. Authenticated transaction-history compaction and multi-version migration require another source unit before production use; replay evidence is never silently dropped.

## Remaining source integration

`StoreIdentity.Installed()` now binds only a genuine LocalService token with an enabled `NT SERVICE\LnwjudUpdateAdmission` service SID to the fixed `CommonAppData/lnwjud/update-admission` store. It refuses ordinary user, SYSTEM and other LocalService tokens without that service SID, and never creates the store or service. This is identity resolution only: the SCM dispatcher is fail-closed, and the new separate create-only SCM provisioner has not been executed or enrolled as a trusted production service. Runtime principals, updater principals and native evidence have private constructors and no production factory. These capabilities still need a real authenticated registry and Windows peer verifier. A pipe request must never mint them from caller-supplied SID, PID, path, claim or boolean.

The new `WindowsUpdateAdmissionPeerObservation` is a read-only prerequisite for a future authenticated pipe endpoint. Given an already-connected server pipe, it queries the kernel-reported client PID, retains a query-only process handle, reads process creation time, image path and token user SID, cross-checks the pipe-reported, process and primary-token session IDs, then rechecks the PID, session and process instance. No production service listener calls it, and its observations cannot mint a `RuntimePrincipal` or authorize installation. A retained handle can establish that the observed process instance remains alive, but **not** that the pipe is still connected, that the same process held the original pipe during the PID-to-handle race, or that a duplicated handle belongs to that process. Unavailable observations refuse rather than become authority.

Pipe peer observations alone are not connection or termination proof. In local Windows probes with server and client in the same process, `GetNamedPipeClientProcessId` continued to return the old PID after the client closed its pipe, before the server attempted further I/O; a server instance also reconnected to the same process with the same handle and PID. These probes do not establish behavior for an installed service or prove that the closed pipe remained usable. A retained process handle identifies that process only after acquisition; the initial PID-to-handle race and inherited or duplicated pipe handles still require an authenticated connection design. Failed or inaccessible observations remain unknown, not evidence that a participant terminated.

The next source unit must implement the attended signed baseline and complete machine membership registry, fixed pipe and SCM composition, peer capture-to-connection authentication (beyond the new read-only PID/token/creation/image observation), authenticated read-only containment service observations, and durable updater-owner cessation/disposition verification. The containment service must remain the sole Job handle owner; this broker must never retain a Job handle or gain generic SYSTEM execution or SeDebug access. Missing or inaccessible service observations must retain admission holds.

Desktop, STDIO, HTTP, ToolRegistry, Goal/background work, shell launch and native service reservations still need admission adapters. They must acquire before any writer effect, promote before releasing parent calls, retain permits until actual settlement, and acknowledge quiescence only after writers, migrations, Goals and database handles are closed. Full Bypass must not bypass maintenance. The application cannot exit for replacement until the current seal covers the complete provisioned membership and all native reservations are released. A scalar active-call count cannot establish that condition.

Guarded create-only image staging, SCM registration and parent/root provisioning sources now exist, but none has passed a trusted elevated installed E2E. Independent image provenance, authenticated store bootstrap and journal freshness, real LocalService/service-SID execution, other-user isolation, SYSTEM service peer authentication, complete writer coverage, service replacement, signed install/health/rollback and native end-to-end acceptance remain unimplemented or untested. These missing source integrations are separate from unavailable signing credentials. This core does not satisfy the full updater acceptance gate or authorize release.

## Isolated verification

The test executable compiles the same `Admission*.cs` sources with `ADMISSION_ISOLATED_TESTS`. Only that separate artifact contains factories for synthetic principals/evidence, an explicit fresh-fixture initializer and a stage-interruption hook. Its initializer creates a permanent marker with `CREATE_NEW` and refuses reuse. It creates private random temporary fixtures owned by the actual TokenUser. The production project does not compile those factories or tests, has no test-root environment switch, and cannot mint production authority. Synthetic evidence tests establish state-machine behavior, not real service authentication or Job proof.

```powershell
dotnet build native/update-admission-broker/tests/UpdateAdmissionTests.csproj --configuration Debug --nologo
dotnet run --project native/update-admission-broker/tests/UpdateAdmissionTests.csproj --configuration Debug --no-build
dotnet build native/update-admission-broker/WindowsUpdateAdmissionBroker.csproj --configuration Release --nologo
```

The harness tests strict framing, generation fencing, closure versus entry, promoted job holds, epoch-bound quiescence, replay refusal, real cross-process lock exclusion, process exit after durable staging, refusal of unverified recovery, CAS conflict preservation, file ownership, unsafe DACL refusal, hard-link refusal and junction refusal. It does not change installed app data, SCM configuration, tunnel state or canonical package pins.
