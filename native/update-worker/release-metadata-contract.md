# Release metadata contract, protocol 1

This is the selected producer/consumer contract for the next implementation unit. It adopts the native consumer sketch's complete previous-package identities, compatibility digests and scoped recovery authorization, and the producer sketch's actual build-attestation verification boundary. The worker remains the sole owner of its protected update transaction. Metadata authentication alone never permits admission closure, publisher acceptance, installation or rollback. The protected native transaction installer remains unavailable until all later units and actual acceptance pass. The Desktop's separate explicit-consent Electron package handoff does not change this contract and is not updater acceptance.

## Signature and structural schema

The exact envelope fields are `protocol`, `keyId`, `payload`, `signature`. Protocol is integer 1. Key ID is 1–64 ASCII letters, digits, dot, underscore or hyphen and selects an embedded root. Payload and signature are canonical padded standard Base64. Signature is exactly 64 bytes of P-256/SHA-256 IEEE-P1363 `r || s`. The signed message is ASCII `lnwjud-update-release-v1`, one NUL byte, and the exact decoded payload bytes. No algorithm negotiation or JSON reserialization occurs during verification.

One tracked `config/update-release-schema.json` defines exact field sets, fixed enum values, primitive bounds and encodings for both implementations. Both decoders consume that resource, rather than maintaining separate structural allowlists. Native embeds it. Domain relationships are checked after structural validation and signature verification. Shared adversarial byte fixtures exercise both decoders. Unsupported schema changes fail closed.

Bounds are 49,152 envelope bytes, 32,768 payload bytes and JSON depth 12. Reject duplicate decoded property names at every depth, unknown/missing/null fields, invalid UTF-8/BOM/surrogates, trailing data, noncanonical Base64, integer exponent/float forms, unrecognized enums and overlong strings before authority is returned. Envelope digest hashes the exact retained outer bytes. Strings carrying identifiers, names and numeric values remain ASCII under the rules below.

## Exact payload fields

All fields listed here are required and every object rejects additional fields.

| Object | Exact fields |
| --- | --- |
| payload | `protocol`, `product`, `policyRevision`, `releaseId`, `channel`, `platform`, `architecture`, `distribution`, `version`, `releaseSequence`, `issuedAt`, `notBefore`, `expiresAt`, `source`, `buildEvidence`, `artifact`, `provenance`, `previous`, `compatibility`, `recoveryAuthorization` |
| source | `repository`, `commit`, `workflow`, `ref`, `runId`, `runAttempt` |
| buildEvidence | `kind`, `artifactAttestationSha256`, `provenanceAttestationSha256`, `sourceTree` |
| artifact/provenance | `name`, `sha256`, `sizeBytes` |
| previous | `version`, `releaseSequence`, `envelopeSha256`, `artifact`, `provenance` |
| compatibility | `migrationContractSha256`, `workerContractSha256`, `serviceContractSha256` |
| recoveryAuthorization | `purpose`, `candidateArtifactSha256`, `candidateReleaseSequence`, `previousEnvelopeSha256`, `previousArtifactSha256`, `previousProvenanceSha256`, `expiresAt`, `maximumAttempts` |

Protocol, product, and channel are `1`, `lnwjud`, and `stable`. The metadata verifier accepts only these exact target identities:

| Platform | Architecture | Distribution | Artifact name |
| --- | --- | --- | --- |
| `win32` | `x64` | `windows-nsis` | `lnwjud-Setup-<version>.exe` |
| `darwin` | `x64` | `macos-zip` | `lnwjud-<version>-x64.zip` |
| `darwin` | `arm64` | `macos-zip` | `lnwjud-<version>-arm64.zip` |

This table defines which signed metadata identities the verifier can authenticate. It does not mean that any platform can install or recover an update. Each target still needs its own enrolled native authority, transaction implementation, signed acceptance receipts, and health and rollback proof before the application may offer automatic installation. Release IDs are 1–128 ASCII letters/digits/`._-`.

Version is canonical stable `major.minor.patch`, no leading zeroes, prerelease or build suffixes; each component is bounded to 2,147,483,647. Digests are 64 lowercase hex; current repository commits are 40 lowercase hex. Positions, sequences, run IDs/attempts and sizes use canonical decimal strings bounded to uint64; sequences/run IDs/attempts/sizes are positive. Times are decimal UTC Unix seconds in 0..253402300799. `policyRevision` and `maximumAttempts` are JSON integers, with the latter exactly 1.

Artifact names must match the target table above; provenance name is exactly `PROVENANCE.json`. They are basenames, never paths/URLs. Production limits cap package size at 2 GiB and provenance at 1 MiB. Source repository is the exact configured `https://github.com/engasnm111/lnwjud`; workflow, ref, immutable builder identity, source commit and selected run/attempt must satisfy configured allowlists. A stable source normally comes from the protected `refs/heads/main` push build selected by existing release promotion, not a tag build invented by the payload.

Build evidence kind is `github-artifact-attestation-v1` and source tree is `clean`. These are authenticated release-authority endorsements of the producer's verified inputs, not independently observed native build-machine facts. Artifact and exact provenance bytes each need actual authenticated build attestations before signing. Attestation digests bind the exact input bundles.

Both candidate and previous artifact/provenance identities include names, sizes and digests. The previous envelope digest binds its exact original authenticated bytes. Recovery purpose is `failed-candidate-only`; its candidate/previous fields must exactly equal their corresponding payload identities and its expiry cannot exceed candidate expiry. It is evidence for one later transaction-bound recovery, not a general downgrade operation.

## Time, baseline and receipts

Protocol 1 issues immediately active offers with `issuedAt == notBefore < expiresAt`. Maximum validity is 86,400 seconds and maximum future issue skew is 300 seconds. Both limits are explicit policy fields and cannot be overridden by a manifest. The producer must provide fresh metadata; expired offers remain unavailable rather than extending their validity locally. An operational refresh mechanism remains necessary before production availability can be claimed.

Native verification requires a native-owned authenticated installed baseline, a trust snapshot with generation/revision, highest accepted sequence, last accepted time and failed candidate digests, and a usable time observation. Missing/uncertain baseline or clock refuses. Time below the retained floor refuses instead of silently using the floor as now. `RetainedInstallationBaseline.Sequence` is the last committed release; `ReleaseTrustSnapshot.HighestAcceptedSequence` is a monotonic anti-replay floor. The production authority must advance that floor in the same CAS that binds explicit user consent to the authenticated offer, before any external update effect. Ordinary offers must exceed both the floor and committed baseline. Rollback restores the exact prior application/data baseline without lowering the floor; recovery is limited to the exact quarantined failed candidate at the current floor and its single authorized attempt. The verifier checks these relationships but does not persist consent or advance the floor. Later admission must CAS-commit and revalidate actual pinned package/publisher evidence before effects.

An expired historical previous descriptor is eligible only for the signed candidate's fresh exact recovery authorization, retained original authenticated installation acceptance, permitted current key history/revocation, compatible recovery contracts, and this exact failed transaction with its one remaining attempt. There is no `ignoreExpiry` flag. Ordinary expiry, revocation, quarantine and anti-replay floors remain enforced. No retained trust record means no unattended baseline. The current unit does not execute recovery.

## Production trust policy and producer

One tracked `config/update-release-policy.json` is embedded in the native assembly and consumed by the producer. Initial release roots, target/source authorities and verifier authority are empty/unconfigured. Production refuses `RELEASE_TRUST_UNCONFIGURED`; it never generates keys, loads public roots from environment/cwd/CLI, adopts downloaded keys or enables test roots. A configured P-256 root has exact key ID, canonical DER SPKI plus digest, allowed release/recovery roles, bounded validity and revocation state. Its explicit `allowHistoricalRecovery` flag defaults to false. Historical verification requires retained original native authenticated acceptance time and identity, that permission and a currently non-revoked historical root; the fresh candidate's release/recovery root must still be currently active. Unsupported rotation or policy revision refuses. Initial root provisioning and protected signer custody are explicit operator work.

The production producer starts a fixed hash/version-pinned GitHub attestation verifier against the actual artifact and exact provenance bytes/bundles. It accepts no saved verification-result JSON, caller `verified` boolean, arbitrary verifier executable/path or identity override. The verified certificate issuer, repository/source ref/digest, signer/config workflow/digests, GitHub-hosted runner and run/attempt identity must match configured policy and the selected exact successful CI source. Subject hashes/names and required verified timestamps are checked. Workflow predicate contents remain workflow-controlled; the audited immutable trusted builder must enforce the clean-source/build contract.

The source authority pins the reusable builder's immutable `builderDigest`. The caller workflow changes with each source release: its explicit `buildConfigDigestRule` is `source-commit`, requiring the authenticated certificate's configuration digest to equal the exact selected source commit and its configuration URI to match the configured caller workflow/ref. Neither an arbitrary future caller digest nor a wildcard is accepted. Unsupported rules refuse.

Only after all evidence subprocesses complete may the producer load its private signing key in process. It derives the public SPKI and requires exact agreement with the configured root, removes the secret environment entry, starts no further subprocess, signs exact payload bytes and verifies its own output. No private key goes into arguments, child environment/stdin, logs, exceptions or files. Output is published only after successful verification, with no partial unsigned envelope or unrelated overwrite.

Production build attestation requires an audited immutable reusable builder that owns checkout of the actual execution SHA, fixed target build/signing, independent clean-source checks and final subject hashing. Grant `contents:read`, `id-token:write`, `attestations:write` only at the appropriate non-PR builder boundary. Release promotion must verify before signing, not merely sign downloaded unsigned provenance. Workflow integration, exact verifier provisioning and issuer/schema compatibility need real evidence; absent authority refuses. Do not invent action revisions, source/builder digests or signing identities.

## Implementation ownership and verification

Producer owner creates shared schema/policy first, Node strict parsing, evidence verification and signing modules, plus focused fixtures. Native owner embeds those exact resources and implements strict metadata/policy/crypto/time/baseline verification. Native stdio retains its current narrow bootstrap commands; no paths, roots or arbitrary verification/install commands are exposed. Test-only policy construction stays inside the friend harness. A valid disposable Node-signed fixture must pass the real .NET verifier and fail production's empty embedded policy.

Both implementations must reject changed bytes, wrong domain/key/curve/signature format, malformed nested data, signed dirty/wrong-source evidence, wrong target/run/builder, time rollback/expiry, replay/quarantine, untrusted previous identity and unauthorized recovery. Missing production authority must leave capabilities unavailable and produce no drain, Tunnel stop, installer, data restore or trust-floor write. Actual native signer/file pinning, global admission, install/relaunch, migration/health, Tunnel restoration and bounded trusted rollback remain required after this metadata unit. The user's no-release-until-actual-updater-acceptance instruction remains in force.

## Initial Windows enrollment metadata preflight

The private native helper command is `lnwjud-containment.exe service-enroll-preflight <absolute-package-directory>`. It accepts exactly one directory argument. The directory contains fixed `RELEASE.json`, `ENROLLMENT.json`, and `PROVENANCE.json` files plus the installer basename authenticated by the release envelope, `lnwjud-Setup-<version>.exe`. The command reads these files; it never executes or installs a package, changes the service, or writes an enrollment record. Malformed argument counts refuse. The embedded empty production policy returns JSON `{"status":"refused","readyToEnroll":false,"reason":"RELEASE_TRUST_UNCONFIGURED"}` with exit 2 before opening the package directory. Valid metadata under a configured policy returns `status=metadata_authenticated`, `readyToEnroll=false`, and `reason=ENROLLMENT_ACCEPTANCE_UNAVAILABLE` with release, layout and policy digests. The latter outcome is metadata authentication only.

`ENROLLMENT.json` is a detached protocol 1 envelope with the same exact four envelope fields and P-256 signature encoding as `RELEASE.json`. Its signed message is ASCII `lnwjud-enrollment-layout-v1`, one NUL byte, and the exact decoded payload bytes. It uses an active release-role key from the embedded policy. `config/update-enrollment-schema.json` bounds it to 32,768 envelope bytes, 16,384 payload bytes and depth 8. Its exact payload fields are `protocol`, `product`, `policyRevision`, `releaseId`, `channel`, `platform`, `architecture`, `distribution`, `version`, `releaseSequence`, `releaseEnvelopeSha256`, `source`, `artifact`, `provenance`, and `layout`. `layout` has exactly `stableLauncher`, `stableService`, `slotApplication`, and `slotManifest`. Each role has `path`, `sha256`, and `sizeBytes`. Paths are ASCII slash-separated relative components; absolute paths, traversal, ADS, reserved device names, trailing dot or space, and case-insensitive duplicate paths refuse. No local install path or SID is signed. The release envelope's exact digest, release identity, target, source, policy revision and artifact/provenance identities must match the layout. The target is Windows x64 NSIS only.

Initial release authentication uses the existing release schema, signature domain, configured source, target identity and time checks without an installed baseline. The ordinary `VerifyOffer` and recovery paths still require their retained native acceptance receipt, trust snapshot, anti-replay and recovery checks. The preflight opens the fixed package files without traversing reparse points, retains directory and file handles while checking identity, size and digest, and compares the installer and provenance to the signed release identities. This hash readback does not independently verify GitHub artifact attestations or prove that the signed role files exist in a protected installed tree. Intended-user binding, local publication, native acceptance and updater availability remain separate later gates. Test signatures use ephemeral keys only; the checked-in policy still has no production trust roots.

## Private Windows artifact attestation preflight

`service-enroll-attestation-preflight <absolute-package-directory>` is a separate helper command. The metadata-only command above keeps its existing meaning. The stronger command additionally requires fixed `artifact.bundle.json` and `provenance.bundle.json`, whose hashes come from authenticated release metadata. It retains all six package handles and the verifier image and ancestor handles until every created Job has an observed zero active-process count. A matching result reports `artifact_attestations_authenticated`, `readyToEnroll:false`, and `ENROLLMENT_ACCEPTANCE_UNAVAILABLE`. It creates no baseline, installed-tree acceptance receipt or enrollment record.

The only verifier deployment path is `update-attestation/gh.exe` beneath the running helper directory. The embedded policy binds its exact SHA-256 and version. No PATH search, package executable, caller-selected policy, saved result, credential, endpoint or command option enters this route. Production policy remains empty and refuses before directory or verifier access. Supplying an approved verifier, builder identity and signing root, extending package integrity evidence to cover that image, Desktop staging and installed-copy plumbing are prerequisites for a configured production release. Existing helper packaging does not provide them. Fixture binaries are not production supply.

One helper operation runs three fixed native commands, version and two retained-bundle attestation verifications. An anonymous native HTTPS GET observes the exact signed run attempt on `api.github.com/repos/engasnm111/lnwjud/actions/runs/<runId>/attempts/<runAttempt>`. It disables credentials, cookies, proxies and redirects and preserves normal TLS verification. The request timeout covers headers and streamed body reads; actual response bytes are bounded to 4 MiB. Network uncertainty, rate limiting or authentication requirements refuse without a token fallback. Bundle verification's credential-isolated environment does not establish that every GitHub CLI internal path can never consult an OS credential store.

Shared strict parsing checks the successful completed push run, exact source and attempt, verified certificate issuer, SAN, source repository/ref/digest, immutable signer identity, source-commit configuration, hosted runner, every verified timestamp and a transparency-log timestamp. It requires a SLSA v1 statement with the exact subject name and digest. At least one fully matching entry suffices. Authenticated provenance must bind the product, version, platform, architecture, clean source, run and one unambiguous matching artifact. Workflow predicate assertions do not supply certificate authority. Integer tokens avoid floating-point conversion and reject fractional/exponent forms and unsafe numeric values.

Each child has a 120-second work limit and a combined stdout/stderr limit of 4 MiB. The operation work limit is 480 seconds. Both pipes drain concurrently. Root exit, EOF and a cancellation request alone cannot release pins. Cleanup attempts cancellation and observed Job zero for 10 seconds. Unknown liveness yields a held owner; the private command reports cleanup pending and stays in the foreground, retrying cleanup until actual zero. It cannot report success afterward. This intentionally allows cleanup to exceed the work budget. Forced host death and crash recovery are not accepted by this unit. Child output and raw exceptions never appear in refusal JSON.

Native fixtures use ephemeral roots, a fixture executable and a run-response hook compiled entirely under `NATIVE_CONTAINMENT_TESTS`. They prove parser and ownership behavior, not real hosted attestation, verifier provisioning, installation or updater availability. Independent source review and current-source installed acceptance remain separate gates.
