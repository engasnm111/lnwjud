# Release metadata producer

This unit implements the exact shared release envelope contract and disposable Node-to-.NET verification fixtures. It does not install, restore, admit an update transaction, provision trust or activate a release workflow.

Run its tests with `node --test scripts/update-trust/release-envelope.test.mjs scripts/update-trust/pinned-verifier.test.mjs`. The shared `tests/fixtures/update-release/metadata-v1.json` contains only disposable public policy, exact signed envelope bytes and malformed cases. No private test key is retained. Both decoders consume `config/update-release-schema.json`.

## Local pinned verifier candidate (Windows x64)

`powershell -NoProfile -File scripts/update-trust/provision-gh-verifier.ps1` downloads the fixed GitHub CLI v2.103.3 Windows amd64 archive from the official release, checks the **pinned archive SHA-256** `98d0cfa794721665d7973dd728c78aff7bd836d58f10f6d7a03568eccb0a22e0`, extracts only `bin/gh.exe`, verifies its **pinned executable SHA-256** `d303d8ac3f5e9438bf7c977b64dd6425513eae46218f8881d30694f28c1d0dfd`, Windows Authenticode GitHub publisher status and exact CLI version, then provisions `tools/update-attestation/gh.exe` without overwriting a conflicting destination. An already downloaded archive can be supplied via `-ArchivePath`. The local binary is gitignored and never committed. Windows packaging now provisions or reuses this **exact SHA-256-pinned executable** and stages it under `resources/native-containment/update-attestation/gh.exe`, the fixed path used by native `AttestationOwner`. This supplies the verifier binary only; production release authorities and installer execution remain disabled until independently authenticated signing and native enrollment succeed. On 7 November 2026, the official release archive matched its published checksum and the extracted executable reported a valid GitHub, Inc. Authenticode signature; the positive provisioning and wrong-archive refusal both executed on Windows.

**This is verifier supply preparation, not production verifier enrollment.** The embedded policy still has `authorities=[]`, `verifier=null`; the packaged verifier is now staged at a pinned fixed path, but signer/verifier isolation, complete native ownership, authenticated production signing, trusted installation, relaunch and rollback remain unproven. Do not populate production policy or enable the updater solely because this candidate was provisioned.

Production policy is the fixed tracked `config/update-release-policy.json`. It currently pins one P-256 public release/recovery root, but `authorities` is empty and `verifier` is null, so `requireConfigured` still refuses production signing. On 7 November 2026, the protected-main public-key inspection [run 42354119977](https://github.com/engasnm111/lnwjud/actions/runs/42354119977) derived SPKI SHA-256 `23991c089a1c5bd441566b8381b4196e570c80ccfe5c174db555f67595c61ee9` from the protected environment secret, matching the tracked public root. The private key was not disclosed; matching a public key does not prove independent signer/verifier isolation or authorize installation. The producer accepts no policy, root, verifier path, saved verification-result JSON or `verified` override. Empty authority fails `RELEASE_TRUST_UNCONFIGURED` before inputs or the signing secret are read.

The CLI takes exactly these name/value pairs:

```
node scripts/update-trust/produce-release-envelope.mjs \
  --payload candidate-payload.json --artifact lnwjud-Setup-VERSION.exe \
  --provenance PROVENANCE.json --artifactBundle artifact.bundle.json \
  --provenanceBundle provenance.bundle.json --previousEnvelope previous-envelope.json \
  --previousArtifact previous-package.exe --previousProvenance previous-PROVENANCE.json \
  --keyId CONFIGURED_KEY_ID --output new-envelope.json
```

The current producer reads and removes `LNWJUD_UPDATE_RELEASE_PRIVATE_KEY_PEM` only after its evidence-check call, requires its derived public SPKI to match the configured root, signs exact bytes and verifies its output. If the secret was supplied to the producer process at startup, however, it already exists in that process during evidence verification. Excluding it from the child environment does not establish isolation from a same-user verifier. The pinned verifier refuses acquisition, input pinning and new verifier invocation whenever the signer-key environment variable exists (even if empty), including when it is injected after acquisition. This is only a process-local guard: it does not establish independent OS-identity isolation or protect against an attacker who controls the verifier process or changes its environment outside the checked invocation boundary. Production signing requires a separate signer identity and an authenticated handoff of the exact evidence before the secret becomes available. The destination is published without replacing an existing file; symbolic errors omit child diagnostics and key material.

The evidence path checks actual artifact/provenance and bundle bytes, exact selected successful GitHub push run/attempt, verified certificate repository/source/signer/config identities, subjects and verified transparency timestamps.

A read-only Windows probe on 7 November 2026 downloaded the historical attested package from [run 41768439521](https://github.com/engasnm111/lnwjud/actions/runs/41768439521) and verified both the installer and provenance against their real offline bundles with the pinned GitHub CLI 2.103.3. The verified certificate identified the protected-main builder at source `f16360c4a7957e7c9a0d8014b90d205d001062a3`, and GitHub CLI emitted a Tlog timestamp with numeric offset (`2026-11-04T11:04:11+07:00`). The selector now accepts canonical numeric-offset timestamps with bounded timezone offsets, calendar round-trip checks and the existing issuance-time limit; malformed dates/offsets still fail closed. A separate read-only invocation of `selectVerifiedAttestation` against that actual verified provenance JSON returned `HOSTED_SELECTOR_COMPATIBLE matches=1`, and the complete local update-metadata suite passed 141/141 assertions. This proves compatibility of the observed historical metadata format, **not** isolated production signing, a signed updater release or installed E2E.

The reusable builder has a fixed immutable `builderDigest`. Caller workflow authority uses only `buildConfigDigestRule: "source-commit"`: its verified certificate digest must equal the exact selected payload source commit, with the configured caller URI/ref. Literal future caller digests and wildcard rules are refused. Workflow predicate claims alone convey no trust. [GitHub CLI verification](https://cli.github.com/manual/gh_attestation_verify) documents the output; the supported timestamp records come from [sigstore-go v1.3.0](https://github.com/sigstore/sigstore-go/blob/v1.3.0/pkg/verify/signed_entity.go).

The Windows x64 executor uses the existing native pin addon at its fixed staging path, bound to `CONTAINMENT_PIN_SHA256`. Loading that addon currently assumes the repository and staged code cannot be changed between its hash check and load; this is not a protected bootstrap. The addon holds the fixed verifier executable and its ancestors against writes/deletion, hashes the executable after pinning and retains that pin through the launched process and pipe close. Exact artifact and attestation bundle inputs are pinned before hashing and remain pinned through verification; before/after hashes alone are not an execution or input pin. Children have bounded output/time and the secret environment entry is excluded. Local Windows tests verify blocked file/ancestor renames, writes, input substitution and the tested process shutdown path. Other platforms refuse `RELEASE_VERIFIER_EXECUTION_UNAVAILABLE`. Actual CI attestation compatibility and protected builder/verifier provisioning are still acceptance work.

The executor requires an explicitly supplied `GH_TOKEN` or `GITHUB_TOKEN` and passes it as `GH_TOKEN`; it creates per-session empty, pinned GitHub configuration files and fixes `GH_HOST` to `github.com`. Tests use a disposable token and a Node fixture, not real GitHub evidence. The current Node process launcher only observes the launched root process and its pipes. It does not prove that every descendant has stopped, that its temporary configuration directory has a protected ACL, or that the addon was pinned before loading. Those gaps and actual `gh` attestation compatibility must be resolved before production signing is enabled.

Previous descriptor verification authenticates exact historical signature and package/provenance identities. An expired descriptor additionally requires explicit historical root permission and current non-revocation. This authenticates release history only. The native consumer separately requires the retained original installation acceptance, trusted baseline, replay/time floors and exact failed transaction before recovery can become eligible. Metadata verification does not execute recovery.

The v2 predecessor metadata check copies its envelope once before reading issuance time and verifying the signature. It checks the authorized transition but does not inspect package or provenance files; the file-aware wrapper verifies those separately. Neither check establishes a protected installed baseline or user consent.

## Version 2 source work

The v2 producer source accepts an explicit `--purpose baseline` or `--purpose update`. Both require `--payload`, `--artifact`, `--provenance`, `--artifactBundle`, `--provenanceBundle`, `--keyId` and `--output`. An update additionally requires `--previousPurpose`, `--previousEnvelope`, `--previousArtifact` and `--previousProvenance`; a baseline rejects those arguments. It validates exact predecessor metadata and bytes, checks real build evidence before reading the signing key, checks the current authorization time again before publication, and refuses to replace an existing output.

The v2 stable identity and signature checks have disposable Node/native tests, and the native metadata-only offer check binds a successor to retained previous signed evidence. These checks are not proof of a protected acceptance receipt, consent, build attestation, admission, installation or recovery. The signer-side verifier still needs proven whole-Job cleanup, protected configuration and actual hosted attestation compatibility. Until those gates and protected native enrollment/transactions are implemented, the embedded policy remains unconfigured despite its pinned public root, and the producer refuses `RELEASE_TRUST_UNCONFIGURED`. No protected v2 signing or installation workflow is activated; the existing builder only prepares unsigned candidates.

`signing-verification-manifest.mjs` parses a bounded v1 manifest with fixed baseline or update file roles, strict IDs and hashes, safe basenames and immutable output. It does not authenticate the producing job, inspect file contents, check the artifact transport, authorize signing or retain checked inputs. Candidate and predecessor roles can reuse names and therefore require separate pinned namespaces. The trusted orchestration and exact-byte binding described in the [identity architecture](../../docs/codebase/2026-10-27-v5.9.0-update-identity-architecture.md) remain unimplemented.

`protected-source-run.mjs` and `.github/workflows/update-signing.yml` implement a read-only, key-free preflight on the protected `main` ref. They check a selected exact-SHA successful push CI run and all seven required hosted jobs (including the credential-free signing candidate build), reject alternate runners and reruns, and require one unexpired attested package artifact and one distinct unexpired signing-candidate artifact, each with exact GitHub API owner/run/SHA, name, declared archive digest and size. Both artifact IDs and digests are returned as observed metadata, not as signing authorization. The preflight additionally requires the GitHub run's unique `referenced_workflows` entry to identify the reviewed reusable builder at immutable SHA `cd833d7df45a8ecf2e87bc89ffb9ee3c85d20406`, matching the caller pin. Missing, mutable, substituted or duplicate references refuse; an explicitly observed `refs/heads/main` reference is accepted only when the independently reported `path@SHA` and `sha` equal the pinned commit. The builder pin and this source preflight must be reviewed and changed together when upgrading builder control code. The preflight never accesses the signing environment or private key. GitHub artifact metadata does **not** prove archive contents or attestations; a passed preflight is not an authority grant, a signed update, or permission to install. The workflow currently produces no release artifact or signature.


The reusable Windows package builder now creates a **credential-free baseline or update candidate** in a separate hosted job after attestation. A baseline uses no predecessor inputs; an update requires both an exact previous GitHub Actions run ID and an artifact ID containing a cryptographically signed prior `RELEASE.json`, the previous Installer and `PROVENANCE.json`. The producer authenticates the previous ECDSA release, hashes the actual predecessor files and enforces higher release sequence, non-downgrade and identical recovery contracts. It refuses absent, modified or unverifiable predecessor evidence and keeps prior files in a separate manifest namespace. It copies the exact attested installer, provenance, bundles, and a strict candidate manifest into a second artifact, with source and protected-builder SHA checks. The installer provenance carries three conservative source-derived recovery contract digests, and the signing verifier must match those exact values before accepting the build evidence. Source-contract equality is only a change detector: it does not prove migration safety, installed transaction effects, rollback health, or Tunnel restoration. The attestation job retains its strict data-only execution boundary; the candidate job has no OIDC attestation permission and no signing secret. GitHub's artifact metadata and the unsigned candidate provide no signature or installation authority. Production release policy is still unconfigured until independent signing/verifier and installed native acceptance are completed.

`signing-workflow-diagnostic.mjs` is a key-free diagnostic for a proposed fixed GitHub workflow. It compares fixed workflow context with API observations for the run, verification job and artifact, requires the observed verifier job to use the GitHub Actions hosted Windows runner group/name/label, rejects reruns, and inspects the expected staged manifest and files. Runner metadata is a fail-closed API check, not cryptographic proof of runner isolation. It never returns signing authority. The named workflow exists only as a protected, key-free **source-run preflight**. The artifact-evidence verifier job, authenticated verifier-to-signer handoff and signer job have not been implemented or tested on GitHub. The diagnostic does not prove the staged files came from the selected artifact, verify attestation bundles, retain files through signing, or authenticate an installation. Its environment values are trustworthy only inside the reviewed fixed workflow; a local caller can spoof them.

`signing-files-diagnostic.mjs` checks the files it reads against a manifest and inspects candidate and predecessor metadata using separate directories. The diagnostic checks snapshots only: it does not pin directories or files through signing, authenticate the supplied policy or manifest, or verify attestation bundles. It cannot authorize a release or guarantee paths remain unchanged after it returns.

`signing-artifact-download.mjs` is a key-free download primitive, not an authorization or archive parser. It sends the token only to the fixed GitHub API endpoint, restricts storage redirects to the two explicitly observed GitHub Azure storage hosts (`productionresultssa8` and `productionresultssa11`; no wildcard), streams at most 5 GiB and compares the archive SHA-256 after the stream ends. On 7 November 2026, a read-only authenticated GitHub artifact API probe observed the `productionresultssa11` redirect for artifact `13564696022` (run `42347187165`); the pinned downloader then retrieved its 235,467-byte ZIP and matched GitHub's declared SHA-256 `29e7e563a6a38d840e57b7cfb62c272e9e36a40d8aa2a1d294576eaf1c4d6354`. This proves compatibility with that observed transport and archive digest only, not ZIP member identity, build attestation or signing authority. The caller must verify the run and artifact identity independently, use a file stream whose underlying handle closure is independently verified, and keep the destination private and quarantined: bytes reach it before the hash check, and the caller must close and delete it on every failure, including invalid arguments. A trusted immutable spool, safe ZIP parsing, role binding and actual attestation verification are not implemented by this primitive. Other GitHub storage hosts fail closed until reviewed. A read-only download of historical artifact `12091525336` matched GitHub metadata on 28 October 2026; that does not validate this project's signing workflow or an update.

`signing-archive-entries.mjs` checks a sealed native archive without extracting or executing members. `withInspectedSigningArchive` requires the manifest hash before it invokes a key-free consumer, then verifies every fixed candidate/predecessor role against the manifest's exact filename, uncompressed size, SHA-256 and ZIP CRC. The deliberately narrow archive profile rejects unknown entries, duplicates, unsafe names, symlinks, encryption, compressed members, comments, multi-disk and ZIP64, and inconsistent local/central headers or data descriptors. The regression fixtures cover this profile, but compatibility with a real `update-package-signing-*` artifact has **not** been established. Historical protected-main CI run `41768439521` contains an attested package but no signing-candidate artifact or `prepare-signing-candidate` job; that run predates the candidate job. On 7 November 2026, an unrelated hosted Playwright-report ZIP (artifact `13564696022`) used DEFLATE method 8, which this deliberately narrow parser rejects; that observation is not a signing-candidate failure. The current candidate upload requests `compression-level: 0`, but the real GitHub-hosted signing archive must still be inspected before claiming compatibility or widening the parser. This is a data consistency check only: it does not authenticate the producer, verify build attestations, pin the control code, create an independent signer or permit update installation. Production authorities and verifier remain unconfigured.
