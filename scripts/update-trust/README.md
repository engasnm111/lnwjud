# Release metadata producer

This unit implements the exact shared release envelope contract and disposable Node-to-.NET verification fixtures. It does not install, restore, admit an update transaction, provision trust or activate a release workflow.

Run its tests with `node --test scripts/update-trust/release-envelope.test.mjs scripts/update-trust/pinned-verifier.test.mjs`. The shared `tests/fixtures/update-release/metadata-v1.json` contains only disposable public policy, exact signed envelope bytes and malformed cases. No private test key is retained. Both decoders consume `config/update-release-schema.json`.

Production policy is the fixed tracked `config/update-release-policy.json`, initially empty. The producer accepts no policy, root, verifier path, saved verification-result JSON or `verified` override. Empty authority fails `RELEASE_TRUST_UNCONFIGURED` before inputs or the signing secret are read.

The CLI takes exactly these name/value pairs:

```
node scripts/update-trust/produce-release-envelope.mjs \
  --payload candidate-payload.json --artifact lnwjud-Setup-VERSION.exe \
  --provenance PROVENANCE.json --artifactBundle artifact.bundle.json \
  --provenanceBundle provenance.bundle.json --previousEnvelope previous-envelope.json \
  --previousArtifact previous-package.exe --previousProvenance previous-PROVENANCE.json \
  --keyId CONFIGURED_KEY_ID --output new-envelope.json
```

The current producer reads and removes `LNWJUD_UPDATE_RELEASE_PRIVATE_KEY_PEM` only after its evidence-check call, requires its derived public SPKI to match the configured root, signs exact bytes and verifies its output. If the secret was supplied to the producer process at startup, however, it already exists in that process during evidence verification. Excluding it from the child environment does not establish isolation from a same-user verifier. Production signing requires a separate signer identity and an authenticated handoff of the exact evidence before the secret becomes available. The destination is published without replacing an existing file; symbolic errors omit child diagnostics and key material.

The evidence path checks actual artifact/provenance and bundle bytes, exact selected successful GitHub push run/attempt, verified certificate repository/source/signer/config identities, subjects and verified transparency timestamps. The reusable builder has a fixed immutable `builderDigest`. Caller workflow authority uses only `buildConfigDigestRule: "source-commit"`: its verified certificate digest must equal the exact selected payload source commit, with the configured caller URI/ref. Literal future caller digests and wildcard rules are refused. Workflow predicate claims alone convey no trust. [GitHub CLI verification](https://cli.github.com/manual/gh_attestation_verify) documents the output; the supported timestamp records come from [sigstore-go v1.3.0](https://github.com/sigstore/sigstore-go/blob/v1.3.0/pkg/verify/signed_entity.go).

The Windows x64 executor uses the existing native pin addon at its fixed staging path, bound to `CONTAINMENT_PIN_SHA256`. Loading that addon currently assumes the repository and staged code cannot be changed between its hash check and load; this is not a protected bootstrap. The addon holds the fixed verifier executable and its ancestors against writes/deletion, hashes the executable after pinning and retains that pin through the launched process and pipe close. Exact artifact and attestation bundle inputs are pinned before hashing and remain pinned through verification; before/after hashes alone are not an execution or input pin. Children have bounded output/time and the secret environment entry is excluded. Local Windows tests verify blocked file/ancestor renames, writes, input substitution and the tested process shutdown path. Other platforms refuse `RELEASE_VERIFIER_EXECUTION_UNAVAILABLE`. Actual CI attestation compatibility and protected builder/verifier provisioning are still acceptance work.

The executor requires an explicitly supplied `GH_TOKEN` or `GITHUB_TOKEN` and passes it as `GH_TOKEN`; it creates per-session empty, pinned GitHub configuration files and fixes `GH_HOST` to `github.com`. Tests use a disposable token and a Node fixture, not real GitHub evidence. The current Node process launcher only observes the launched root process and its pipes. It does not prove that every descendant has stopped, that its temporary configuration directory has a protected ACL, or that the addon was pinned before loading. Those gaps and actual `gh` attestation compatibility must be resolved before production signing is enabled.

Previous descriptor verification authenticates exact historical signature and package/provenance identities. An expired descriptor additionally requires explicit historical root permission and current non-revocation. This authenticates release history only. The native consumer separately requires the retained original installation acceptance, trusted baseline, replay/time floors and exact failed transaction before recovery can become eligible. Metadata verification does not execute recovery.

The v2 predecessor metadata check copies its envelope once before reading issuance time and verifying the signature. It checks the authorized transition but does not inspect package or provenance files; the file-aware wrapper verifies those separately. Neither check establishes a protected installed baseline or user consent.

## Version 2 source work

The v2 producer source accepts an explicit `--purpose baseline` or `--purpose update`. Both require `--payload`, `--artifact`, `--provenance`, `--artifactBundle`, `--provenanceBundle`, `--keyId` and `--output`. An update additionally requires `--previousPurpose`, `--previousEnvelope`, `--previousArtifact` and `--previousProvenance`; a baseline rejects those arguments. It validates exact predecessor metadata and bytes, checks real build evidence before reading the signing key, checks the current authorization time again before publication, and refuses to replace an existing output.

The v2 stable identity and signature checks have disposable Node/native tests, and the native metadata-only offer check binds a successor to retained previous signed evidence. These checks are not proof of a protected acceptance receipt, consent, build attestation, admission, installation or recovery. The signer-side verifier still needs proven whole-Job cleanup, protected configuration and actual hosted attestation compatibility. Until those gates and protected native enrollment/transactions are implemented, the embedded production policy remains empty and the producer refuses `RELEASE_TRUST_UNCONFIGURED`. No v2 workflow is activated.

`signing-verification-manifest.mjs` parses a bounded v1 manifest with fixed baseline or update file roles, strict IDs and hashes, safe basenames and immutable output. It does not authenticate the producing job, inspect file contents, check the artifact transport, authorize signing or retain checked inputs. Candidate and predecessor roles can reuse names and therefore require separate pinned namespaces. The trusted orchestration and exact-byte binding described in the [identity architecture](../../docs/codebase/2026-10-27-v5.9.0-update-identity-architecture.md) remain unimplemented.

`signing-workflow-diagnostic.mjs` is a key-free diagnostic for a proposed fixed GitHub workflow. It compares fixed workflow context with API observations for the run, verification job and artifact, rejects reruns, and inspects the expected staged manifest and files. It never returns signing authority. Its workflow has not been created or tested on GitHub. The diagnostic does not prove the staged files came from the selected artifact, verify attestation bundles, retain files through signing, or authenticate an installation. Its environment values are trustworthy only inside the reviewed fixed workflow; a local caller can spoof them.

`signing-files-diagnostic.mjs` checks the files it reads against a manifest and inspects candidate and predecessor metadata using separate directories. The diagnostic checks snapshots only: it does not pin directories or files through signing, authenticate the supplied policy or manifest, or verify attestation bundles. It cannot authorize a release or guarantee paths remain unchanged after it returns.

`signing-artifact-download.mjs` is a key-free download primitive, not an authorization or archive parser. It sends the token only to the fixed GitHub API endpoint, restricts storage redirects to the one observed GitHub storage host, streams at most 5 GiB and compares the archive SHA-256 after the stream ends. The caller must verify the run and artifact identity independently, use a file stream whose underlying handle closure is independently verified, and keep the destination private and quarantined: bytes reach it before the hash check, and the caller must close and delete it on every failure, including invalid arguments. A trusted immutable spool, safe ZIP parsing, role binding and actual attestation verification are not implemented by this primitive. Other GitHub storage hosts fail closed until reviewed. A read-only download of historical artifact `12091525336` matched GitHub metadata on 28 October 2026; that does not validate this project's signing workflow or an update.
