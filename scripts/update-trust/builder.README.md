# Immutable Windows package builder source

`update-package-builder.yml` is a reusable workflow only. No caller is changed, so this unit does not start a build, create a release, configure a signing key or make automatic installation available. A later reviewed caller must reference the actual commit containing this workflow and its control code by its full immutable SHA. It must run only for the allowed main-push CI context. There is no fabricated self-commit placeholder.

The resolver is trusted inline code in the immutable workflow itself. It requires GitHub's `GITHUB_REF_PROTECTED` observation to be `true`, reads the exact current public GitHub run/attempt, and requires the allowed repository/caller/source and a unique `referenced_workflows` entry whose `path@40-character-SHA` equals its resolved SHA. A named ref is refused: its optional `ref` must be absent or equal that literal SHA. GitHub can normalize a mutable/local reference's `path` to a SHA while still reporting `ref: refs/heads/main`, so the path alone is insufficient. Both later jobs independently check out the actual immutable control commit. Caller source is checked out separately at the real execution SHA, with checkout credential persistence disabled.

The build job has only `contents:read`; no OIDC, attestation permission or signing input. Control rejects known publisher/envelope signing entries and build-job OIDC credentials. It verifies the initially clean source HEAD, runs the fixed full canonical Windows release verification command, refuses all unexpected source changes, and independently derives the exact three supported generated integrity sources from actual staged bytes. Those generated sources cannot hide extra executable statements. Only the exact Setup and provenance pair is staged, hashed and uploaded.

This credentialless package is an unsigned metadata/build subject, not an accepted signed update. Existing provenance accurately records signing state. Actual publisher acceptance remains a separate updater gate. Build/project code belongs to the reviewed protected-source trust boundary; this workflow does not claim a sandbox against hostile code with the same OS user or independent observation of historical compiler behavior.

The attestation job starts on a fresh runner. It checks out the same immutable control commit, downloads only the exact build artifact ID from its current run, rejects directories/links/extra subjects, checks context and final hashes, and executes no downloaded script or executable. Two pinned official attestation action calls sign the exact Setup and exact provenance digest/name independently. Control retains the exact returned bundles only after subject readback. The final artifact contains precisely Setup, `PROVENANCE.json`, `artifact.bundle.json` and `provenance.bundle.json`. Bundle retention is not a substitute for the separate producer's real certificate/transparency verification.

Run isolated source tests with `node --test scripts/update-trust/builder-control.test.mjs`. They execute the actual inline resolver with bounded mock HTTPS data and exercise filesystem hashing/refusals and generated-source derivation. They do not run native preparation, packaging or a hosted workflow. A real allowed-run attestation/certificate inspection is still required before any production authority is configured.
